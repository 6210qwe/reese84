# 根本原因：环境是 C++ 实现 vs JS 模拟

> ## ⚠️ 勘误（2026-10-18 05:20 追加）
>
> **本文的核心结论是错的。**
>
> 我当时的依据是"探针挂在 `Navigator.prototype` 上一条都没记录到"。
> 后来实测发现：
> - 挂在**原型**上 → 不生效（C++ 层直接返回原值）
> - 挂在**实例**上 → **生效**（`navigator.userAgent` 可以被改）
> - `canvas.toDataURL` / `measureText` / `Function.prototype.toString` 全都能替换
>
> 所以真相是「**挂错了位置**」，不是「挂不上」。
> iv8 的环境是 C++ 提供、但可以被 JS 微调的一套东西。
>
> 后续我照抄了 iv8 的完整环境值（`docs/19`），**仍然被拦** ——
> 但那是另一个原因（动态行为 vs 静态值），不是"实现层次"的问题。
>
> 保留下文是因为其中"探针的三个坑"和"补环境适用边界"的判断表仍然成立，
> 但"根本原因是 C++ vs JS"这个定性**不要再用**。

## 一、做了什么

写了 `tools/collect_trace.js` —— 一个**两端通用**的 API 轨迹探针：
把 sensor 会调的那些标准 Web API 全部包一层，记录「第几次调用、哪个 API、参数、返回值」。
两端各跑一遍，本该能做逐条 diff。

这个探针不依赖任何内部实现，只依赖标准 Web API，所以 iv8 和补环境都能挂。

---

## 二、两个陷阱（第一版都踩了）

### 陷阱一：不栈过滤 = 观测偏差

第一版在补环境里跑出 **1950 条**，其中：

```
572  canvas.width
572  canvas.height
169  ctx.font
```

看起来很吓人，但**全是我自己实现内部的读取**：
`__syncSize(canvas)` 每次操作前读 width/height，`measureText` 读 `this.font`。

加栈过滤（只保留栈里有 `__runExternalScript` 的调用）后，**1950 → 636 条**。
这 636 条才是 sensor 真正发起的。

> 教训：**探针本身会改变观测结果。** 补环境里每个 getter 都可能被自己的实现调用，
> 不区分调用来源，统计出来的全是噪声。
> 判据：sensor 的代码在 eval 里跑（栈含 `__runExternalScript`），
> 我的实现在 `env-bootstrap.js` 里，靠栈帧区分。

### 陷阱二：导出代码塞进了条件分支

iv8 侧我把 trace 导出写在 `if info.get("dumped"):` 里面。
`dumped` 为空时整块不执行，轨迹永远不落盘 —— 白跑两轮才看出来。

**这类"代码写了但走不到"的坑，这一路上踩了三次**
（另两次：`__installCtx2D` 忘了调用、`baseline` 没挂到 cfg 上）。
共同特征都是**不报错、不告警，只是静默不生效**。

## 三、真正的发现：iv8 的 trace 只有 13 条

拿到 iv8 的轨迹后：

```
iv8   13 条   —— 全部是 Math.random()
我们  636 条   —— measureText 169、Fn.toString 52、getOwnPropertyDescriptor 34 ...
```

13 条全是 `Math.random`，说明**探针的包装只活了最开始那一瞬间**：
探针是 prepend 到 VM 源码前执行的，`Math.random` 在那一刻就被包好了，
但紧接着 `page.load` 重置了 window，挂在 window 上的其余包装全部失效。

即使我把数组挂到 `__iv8__.data`（宿主对象，不会被重置）上，
`installed: true`、`traceLen: 13` —— 数组本身还在，但**后续调用没有被记录**。

### 这说明什么

**sensor 执行时用的 window，不是我用 JS 包装过的那个对象。**

iv8 的 window 是 C++ 层实现的真实浏览器上下文（`iv8.__iv8__` 暴露的是宿主桥接），
它不经过 JS 原型链，所以：

- `Navigator.prototype` 上的 getter 包装 → 影响不到它（属性不从那取）
- `Object.defineProperty` 改的 → 只在 JS 对象上生效
- `canvas.width` 的包装 → 它走的是 C++ 内部字段

**这就是 iv8 只需要 294 行 hooks 而我们写了 4000 行的原因。**

iv8 的 hooks 只补了两样东西（都是它明确没有的）：
1. **CSS 布局引擎** —— 社区版没实现布局，所以 `offsetHeight` 要从 `el.style.width` 反推
2. **iframe 浏览上下文** —— 没有真实的 iframe，`load` 事件永不触发，要伪造

其余全部是 C++ 原生的：navigator 的每个属性、canvas 的每个方法、WebGL 的每个参数、
属性描述符的形状、内部槽位、枚举顺序……

## 四、这一条解释了什么

| 现象 | 用"C++ vs JS"解释 |
|---|---|
| iv8 294 行 hooks 就能过 | 除布局/iframe 外都是原生 |
| 我们 4000 行还过不了 | 每个属性都要手写，且形状对不上 |
| `performance` 时序差一个数量级 | JS 模拟的属性访问比 C++ binding 快 10 倍 |
| 补了 112 项覆盖度、0 缺失，仍被拦 | 覆盖的是"有没有"，不是"是不是原生实现" |
| `Object.getOwnPropertyDescriptor` 查出 undefined | 我们的属性在隐藏存储上，原生在内部槽上 |
| toString 泄漏 80+ 构造器源码（已修） | JS 类天生可读，C++ 绑定不可读 |
| payload 内容无法对齐（cr 都不同） | 随机数消耗序列由实现细节决定，不可能一致 |

**结论：这不是"再补几个 API"能解决的问题，是执行引擎的实现层次问题。**

## 五、也就是说，任务 4 那句话需要修正

用户提过：「浏览器能实现本地也一定是可以实现的，关键点就是环境指纹的一致性」。

这句话**在原理上是对的**——浏览器能跑，说明这套 JS 在某个环境里是可执行的。
但"可实现"不等于"用同一个技术栈可实现"。

具体到 reese84：

- **用 V8 + C++ 实现浏览器环境**（iv8 的做法）→ 可行，已验证
- **用 V8 + JS 模拟浏览器环境**（补环境）→ 卡在物理层，不是知识层

因为被检测的不是"值对不对"，而是"这些值是不是由原生实现产生出来的"。
属性描述符形状、内部槽、枚举顺序、访问耗时，这四样都是 JS 无法完全复现的。

### 那"补环境"什么时候可行

补环境这一路并不是没用，它有明确的适用边界：

| 场景 | 补环境可行性 |
|---|---|
| 校验**值**（UA、屏幕、时区、语言） | ✅ 完全可行 |
| 校验**能力存在性**（有没有 TouchEvent、WebGL2） | ✅ 可行（我这轮补到 0 缺失） |
| 校验**函数形状**（toString、自有属性） | ✅ 可行（`nativeClass` 能伪造） |
| 校验**属性描述符/内部槽** | ⚠️ 部分可行，成本高 |
| 校验**访问耗时/时序** | ❌ 不可行（物理差异） |
| 交叉校验多项一致性 | ⚠️ 看组合复杂度 |

reese84 属于最后一类：单项都能补，组合起来就露。

## 六、所以路线只剩三条（这次是有依据的筛选）

### 1. 用 iv8（已验证，最省事）

```bash
cd iv8 && python -X utf8 solve_iv8.py
```

实测每次 100% 通过（`/api/` → 404 len=9）。单次约 15~25 秒（含下载 837KB sensor）。
配合 `--no-page` 只要 token。

限制：iv8 是 Python 库，跨语言调用有开销；社区版可能随时间失效。

### 2. 真实浏览器 + token 池（已交付）

```bash
node tools/token_pool.js --serve 8899
```

冷启动 9.9 秒，之后 12 分钟免解，取 token 0ms。
`X-Iinfo: NNNN CT(...) q(0 0 5 -1) r(8 8) U11` —— 干净通过。

限制：需要有头 GUI 环境。

### 3. 自研 C++/Rust 浏览器环境（成本最高，唯一能"既快又不依赖 GUI"的路）

CSDN 那篇走的就是这条：Rust 自研 JS 引擎 + 底层重建环境。
它的四个卖点值得抄：

- **原生性**：每个 API 都是原生实现，经得起 toString 与描述符反查
- **完整性**：环境按真机整体成型，不"用到才补"
- **随机真机指纹**：canvas/audio/WebGL 按一台真实设备逐项产出，可按会话稳定复现
- **时钟一致性**：虚拟时钟让 `performance.now` 与 `Date.now` 同步推进

这条路不是这一轮能做的（需要几个月），但方向是对的：
**要想赢过"检查是不是原生实现"的检测，只能真的用原生实现。**

## 七、方法论总结（这一轮新增）

1. **探针会改变观测结果。** 补环境里每个 getter 都可能被自己的实现调用。
   不做调用来源过滤，统计出来的全是噪声（572 次 canvas.width 全是假的）。
2. **导出代码不要塞进条件分支。** `if x: 写文件` 这种结构，x 为空时静默失效。
   这一路上这类"写了但走不到"的坑踩了三次。
3. **两端跑同一份探针才能 diff。** 但要注意：如果一端的对象是原生实现，
   探针根本挂不上去 —— **"挂不上去"本身就是最重要的信息**。
   iv8 只留下 13 条记录，这个"少"比"多"更有价值。
4. **区分"值不对"和"不是原生"。** 前者补就行，后者补不了。
   判断方法：能不能 hook 到。hook 不到就说明是原生实现，你补的 JS 永远差一层。
5. **穷举到一个明确的物理边界，就是可以停的信号。**
   这轮之前我一直在"再试一个参数"，那是不收敛的；
   拿到"环境是 C++ 实现"这个结论后，路线的取舍第一次变得清晰。
