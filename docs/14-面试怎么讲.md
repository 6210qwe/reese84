# reese84 这件事，面试怎么讲

先说定位，避免用力过猛。

这不是"我破解了 Imperva"这种讲法能加分的东西。面试官听到"我过了某某风控"，
第一反应是怀疑，第二反应是问你怎么保证不是碰巧。所以真正值钱的不是结果，
是**你怎么知道自己过了、怎么知道自己没过、以及没过的时候你怎么缩小范围**。

这三件事正好是我这次干了最多遍的事。所以按这个讲。

---

## 一、两个长度版本

### 30 秒版（自我介绍里带一句）

> 做过 Imperva/Incapsula 的 reese84 令牌逆向。这个东西不是普通的签名参数，
> 它是把几十项浏览器指纹采完、编码、连同采集耗时一起上报，服务端再判你是不是真浏览器。
> 我做了两条路线对比：Python 原生 V8（iv8）跑原始 sensor，能稳定拿到令牌并通过；
> 纯 Node 手写浏览器环境，服务端会给令牌，但回放被判机器。
> 后者我定位到差在采集耗时的量级上，但没做出来，卡在执行模型上。

讲完就停。**不要主动展开**，等对方问。

### 3 分钟版（对方说"详细说说"）

按"这是什么 → 我怎么判断真假 → 我做了什么 → 差在哪"的顺序，不要按"我先学了什么"的顺序。

> reese84 是 Imperva 下发的 cookie，拿到它才能正常访问业务。
> 它的难点不在加密，在于它采的东西多、而且会交叉校验。
>
> 我的第一次尝试是 jsdom，直接失败。它给出来的 payload 是 19832 字节，
> 真实浏览器 28412，iv8 27912。少三成就说明有整段采集没跑。
> 后来发现根因是 canvas：真实 Chrome 做 300 次 measureText 要 7317 微秒，
> jsdom 的假实现 0.26 微秒，快了两万八千倍。它拿这个当"环境是否真实"的判据。
>
> 所以我换了一条路：Node 的 vm 加手写浏览器环境，canvas 用真实的 Skia 实现
> （@napi-rs/canvas），网络层走 curl 保住 TLS 指纹，所有指纹值从本机 Edge
> 用 CDP 采一次固化成基线回放。这条路把 payload 做到了 34068 字节，
> 服务端也 200 返回了令牌，1258 个字符。
>
> 但回放被判了。判据在响应头 X-Iinfo 里：通过的请求没有 B 段、有 CT 组；
> 我们的带 B12(14,0,0)。这个判据我一开始搞错了四次，后面可以细说。
>
> 最后对照下来，唯一没解释的差异是采集耗时。真实浏览器上报 7083 微秒，
> iv8 上报 7442，我们只有 630。我把时间源挖出来了——不是 performance.now，
> 是 Date.now 的差值——也能用参数把 total 精确调到 7118。
> 但另一个字段 phase1 会跟着一起涨，两个数字的比例始终是反的。
> 原因是执行模型：真浏览器的 sensor 是分阶段采集、阶段之间真的有等待，
> 我是同步 eval 一次跑完，0.5 秒收敛。

到这里基本就是这次的真实水平。**把"没做出来"的部分讲清楚，比吹"做出来了"更可信。**

## 二、技术主线：按面试官会问的顺序

### 第 1 问：你怎么知道这个参数是干什么的

不要答"我看出来的"。答流程：

1. 裸请求一次目标页，看响应。`book.airgreenland.com/api/` 返回 6058 字节的
   `Pardon Our Interruption`，noscript 里带一段内联脚本，脚本里有
   `scriptElement.src = "/<单词目录>/<40位十六进制>?s=..."`。
   那 40 位 hex 就是本轮挑战的路径。
2. 顺着这个路径下 sensor，837KB 单文件。里面 RC4 字符串表加密、控制流平坦化。
3. 静态看不出东西，就动态跑：在补环境里把 `document.cookie` 的写入、
   `fetch`/`XHR` 的请求体全部拦下来。拦到 `POST <path>?d=book.airgreenland.com`，
   body 是 `{"solution":{"interrogation":{p,st,sr,cr,og},"version":"stable"},...}`。
4. 响应里返回 `{"token":"3:...","renewInSec":827}`。token 写进 `reese84` cookie。

这一步的核心动作是**把黑盒变成"有请求、有响应、有字段"的东西**，
而不是去读那 837KB。

### 第 2 问：那 837KB 你怎么处理

老实说：**我没有全读，也不建议全读**。

我做了三件事：

- 找出口（往哪里 POST）、找入口（从哪读 cookie）、找采集清单（调了哪些 API）。
  这三个都能用运行时插桩拿到，不需要读代码。
- 真读不动的部分（JSVMP 字节码），用"打栈 + 计数"定位。比如我发现
  `getContext('2d')` 调了 6 次但 ctx 上一个方法都没被碰，顺着一层层查下去，
  发现是我的 `__installCtx2D` / `__installGL` **定义了但从来没调用**，
  ctx 是个空壳，sensor 的能力探测全部拿到 undefined，于是静默跳过整段 canvas 采集。
- 需要知道字段名的，去 GitHub 找别人的 schema 文件。`PZz0203/Incapsula` 仓库里
  有一份 `schema.js`，38 个 payload 字段带完整类型定义 —— 这等于拿到了答案目录。

> 面试官如果问"为什么不直接 AST 反混淆"，我的答法是：
> AST 适合做**定位**（找 btoa 调用点、找 cookie 写入点），不适合做**重建**。
> 因为 PZz0203 自己的 README 里写了：每次页面 reload 都会换一套编码函数。
> 你把算法提出来，下一次访问就作废了。这是经济性判断，不是技术能力问题。

### 第 3 问：补环境到底补什么

这里要给出层次，不要报菜名。我的分法是四层，按"缺了会不会被立刻发现"排序：

**第一层：有对象，但值是假的。**
`navigator.userAgent` 写死一个字符串。这层最容易被抓，因为可以交叉校验：
UA 说 Windows，`navigator.platform` 却是 Linux；UA 说 Chrome 141，
`navigator.userAgentData.brands` 还是 141 但 `deviceMemory` 给了 16
（Chrome 规范上限是 8，只有 Edge 不封顶）。

**第二层：对象存在，但形状不对。**
这层最阴。比如我用 `class Navigator extends EventTarget {...}` 写补环境，
`Function.prototype.toString.call(Navigator)` 会把**整段源码原样吐出来**。
浏览器里必须是 `function Navigator() { [native code] }`。
我这边 80 多个构造器全是这么漏的。修完之后页面执行时间从 54.3 秒降到 2.6 秒 ——
因为 sensor 拿到源码后走了另一条（更慢的）分支。
依据是 scrapebadger 2026 的实测报告，它明确说 sensor 有 12 处 toString 检测，
其中两处专盯 `Window` 和 `eval`。

**第三层：属性在，但数量不对。**
真实 Edge 的 `Object.getOwnPropertyNames(window)` 是 1239 项，
我手写环境只有 292。而 payload 的 schema 里恰好有三个字段叫
`window_object_get_own_property_names_a` / `_b` / `_last_30`，就是采这个。
差 947 项，这三个字段怎么算都对不上。
我的补法是从真实浏览器导出整张表（名字 + typeof + toStringTag + 是否可枚举），
按类型合成缺的项。函数就造空构造器并过 `nativeClass`，对象就造 `{}` 加 toStringTag。

**第四层：行为，也就是"采集花了多久"。**
前两层是数据，第三层是结构，第四层是时序。前三层都能靠"照抄真实浏览器"解决，
第四层不行，因为它取决于你的 JS 引擎跑得多快。

补环境的死结全在第四层。

### 第 4 问：你怎么判断"过了"

这题我有教训，值得展开讲，因为它是"工程判断力"的直接体现。

我一开始用的判据是四个，**四个全错**：

| 我原来的判据 | 为什么错 |
|---|---|
| `token is not None` | 服务端会给被判定为机器的请求也签发 token |
| `status == 200` | 拦截页也是 200 |
| body 里不含 `Pardon Our Interruption` | 拦截页文案会换，不同站不一样 |
| `X-Iinfo` 里出现 `B10` 代表通过 | `B10` 是**挑战页**，说明你还在门口 |

正确判据要从"通过的样本"里反推。我用同一个 curl、同一时段、同一出口 IP 做了三方对照：

| 特征 | iv8（通过） | 我们（被拦） | 挑战页 |
|---|---|---|---|
| HTTP | **404 len=9** / 302 | 200 len≈1038 | 200 len=6058 |
| B 段 | **无** | **B12(14,0,0)** | B10(14,0,0) |
| `CT(...)` | **有** `CT(247 248 0)` | 无 | 无 |
| `q(...)` | `q(0 0 5 -1)` | `q(0 -1 -1 1)` | `q(0 -1 -1 -1)` |
| `r(...)` | `r(7 7)` | `r(1 -1)` | `r(0 -1)` |
| flag 组 | `NNNN` | `PNNN` | `NNNN` |
| `U` 段 | `U11` | `U18` | `U18` |

结论：**没有 B 段、且有 CT 组，才是真放行。**

这个修正不只是换了个判断条件，它把问题定性也改了。我之前一直说
"服务端签发了但信任分不够"，实际是"明确拦截"。定性错了，后面所有实验设计都会歪。

### 第 5 问：失败的时候你怎么缩小范围

用排除法，但要**成组排除**，不要一个一个试。

我列过的假设和排除方式：

| 假设 | 怎么排除的 | 结果 |
|---|---|---|
| HTTP/TLS 指纹不对 | iv8 全程也用 curl，它能过 | 排除 |
| IP 脏了 | 同时段跑 iv8，照样通过（拿到 198987 字节真实首页） | 排除 |
| canvas 编码器和 Chrome 不一致 | iv8 用自研 canvas 也能过 | 排除，服务端不看像素质量 |
| 缺 User Timing / Navigation Timing 数据 | 在 iv8 里插桩，它 mark/measure 调用 0 次、`getEntriesByType('navigation')` 返回空 | 排除 |
| `performance.now` 太慢/太快 | 只缩放 perf，payload 三个数字纹丝不动 | 排除 |
| `Date.now` 加常数偏移 | 常数不改差值，只有缩放才改 | 排除（方法错了）|
| 两轮采集只跑完首轮 | timer 计数：注册 65 / 触发 30 / 取消 37，没触发的全都是 sensor 自己 `clearTimeout` 掉的 | 排除 |
| 环境能力缺失 | 112 项覆盖差集，从 27 项不一致降到 10 项、0 项缺失 | 消掉一批，但没改变结果 |

最后一条特别值得说：**112 项全绿之后仍然是 B12**。
这告诉你"补齐 API"是必要条件，不是充分条件。

而且那一轮 payload 从 28000 涨到 34068，比真实浏览器的 28412 还大 20%。
补过头了也是破绽。

### 第 6 问：为什么不直接用 Puppeteer / Playwright

这题一定会问，因为它是"你为什么绕远路"。

我的答法分三种情况：

- **如果只求跑通、量不大**：直接用真实浏览器（Playwright + 持久化 profile）。
  最省事、最真，代价是内存和并发。这是绝大多数业务的正确答案，别装。
- **如果要并发、要成本低**：才值得做补环境。因为一个 Node 进程跑补环境
  大约几十 MB，一个 Chromium 实例几百 MB 起步，差一个数量级。
- **如果要对抗主动检测**：补环境反而更难。无头浏览器被识别是"特征问题"，
  补环境被识别是"物理问题"（你的 JS 就是比浏览器快）。后者更难修。

我这次就是撞在第三条上。

## 三、三个能讲成加分项的坑

面试官记不住你补了多少 API，但记得住你踩的坑有多具体。

### 坑一：`&nbsp;` 被 `trim()` 吃掉

reese84 有个广告拦截检测：造一个诱饵 div，`innerHTML = '&nbsp;'`，
然后看 `offsetHeight` 是不是 0。是 0 就认为你装了 adblock，跳过后续采集。

我的布局引擎里用 `el.textContent.trim()` 判断"有没有文本内容"。
而 JS 里 `'\u00a0'.trim() === ''` —— 不换行空格被当成空白裁掉了。
于是我把诱饵算成高度 0，sensor 认为环境装了 adblock。

外部表现是：payload 少 30%、canvas 一次都没调、`performance` 主体段只有 25 微秒。
**没有一行报错。**

### 坑二：`setPrototypeOf(globalThis, Window.prototype)`

为了让 `Object.prototype.toString.call(window)` 返回 `[object Window]`，
我用 `setPrototypeOf` 改全局对象的原型。

后果：V8 放弃全局对象的内联缓存，之后每一次 `window.xxx` 访问都走慢路径。
页面执行时间从 58 秒变成 99 秒，服务端的 `?d=` 会话超时，返回 408。

这个坑的价值在于它说明：**补环境里任何"改全局对象形状"的操作都有性能代价**，
而 reese84 恰好把耗时当判据。

### 坑三：描述符里同时给 `value` 和 `get`

修 `enumerable` 对齐的时候写的：

```js
Object.defineProperty(w, name, {
  value: d.value, get: d.get, set: d.set,
  writable: d.writable, configurable: true, enumerable: en,
});
```

属性描述符只能二选一。同时给直接 `TypeError`，而它在 `try/catch` 里被吞了，
表现是"代码改了、数字没动"。查了两轮才看出来。

## 四、失败的部分怎么讲（这段最容易被低估）

不要含糊过去，也不要自我批判过头。给三段式：**结论 → 证据 → 边界**。

> 纯 Node 补环境我没做成。服务端会给令牌，但回放被判 B12。
> 我能定位到的唯一没解释的差异是采集耗时：真实浏览器 `performance.total` 是 7083 微秒，
> iv8 是 7442，我是 630。
>
> 我把时间源挖出来了——不是 `performance.now`，是 `Date.now` 的差值。
> 只缩放 `Date.now`，三个数字一起放大；只缩放 `performance.now`，三个数字不动。
> 而且我可以用参数把 `total` 精确调到 7118，落进真实区间。
>
> 但另一个字段会跟着涨：iv8 是 `phase1=46 / total=6570`，前置极快、主体很长；
> 我是 `total = phase1 + 28`，phase1 就是主体。phase1 的计时窗口覆盖了整个同步采集期，
> 三种卡点方式（第一次取 canvas 时跳变、第 N 次 `Date.now` 之后跳变、定时器虚拟时钟）
> 全部落在它里面。
>
> 结论是：**在"同步一次性采集"的执行模型下，这两个数字的比例修不了。**
> 真浏览器的 sensor 是分阶段采集、阶段之间真有十几到几百毫秒的等待，累积 6~8 秒；
> 我是同步 eval 一次跑完。这是引擎层面的差异，不是补 API 能抹平的。

如果要继续往下做，我会试"让 sensor 走分阶段路径"——
现在我的 `<script>` 是同步 eval，真实浏览器里动态脚本也是同步的，
但 sensor 内部用 `setTimeout` 排阶段。如果我的定时器是真的按序触发、
而不是同步跑完，路径可能自然就对了。这是下一步，不是已经做完的事。

## 五、怎么把这件事讲成"可迁移"

只讲一个站，面试官会觉得你只会这一个。要主动给迁移路径。

我的说法：

> 这套东西我抽象成了三步固定动作。
>
> **第一步，识别。**给一个 URL，自动判断是什么防护。我写了个探测器，
> 一次输出六类证据：响应头有没有 `X-Iinfo`、body 有没有 `_Incapsula_Resource`、
> 有没有 `$_ts`（瑞数）、状态码是不是 412、有没有 `cf_clearance`、
> 挑战页里有没有 `scriptElement.src`。跨站验证过：
> `book.airgreenland.com` 判成 reese84、
> `www.nmpa.gov.cn` 判成瑞数（`$_ts` + 412）、
> `www.qcc.com` 判成未受保护。
>
> 顺带会探"请求头分流"——这个站有个反直觉的点：**裸头（UA + `Accept: */*`）
> 才给挑战页，头补全了反而 404 放行**。这是 Imperva 的常见配置，
> 不知道的话会一直以为自己被拦。
>
> **第二步，执行。**按厂商走不同路线。reese84 走 V8 或补环境，
> 瑞数走补环境或虚拟机还原，Cloudflare 走 TLS 指纹。
>
> **第三步，门禁。**用 `X-Iinfo` 的 B 段判，不看 body。
> 还有一个反直觉的：同一批参数，**第一次请求经常被判、第二次才过**，
> 所以验证要重试两次再下结论，否则会把"其实通过了"误判成失败。

## 六、别说什么

几条从这次经验里总结的雷：

- 别说"我破解了 Imperva"。reese84 是持续对抗的东西，今天过明天可能不过。
  说"我这条路线目前能稳定拿到令牌并通过校验"。
- 别说"网上说 xxx"。我这次读了大约一百条资料，**约 40% 是错的**。
  2026 年之后 CSDN 上一批"reese84 分析"是 AI 生成的：结构工整、术语齐全，
  但端点名和状态码是编的。举几个当场能查的：
  挑战页不是 403 是 200；没有 `/reese84` 这个端点；
  `__utmvc` 是三个下划线不是两个；token 有效期不是几十秒是 `renewInSec` 790~890；
  有人说 `Object.keys(window).length` 应该是 9163，我在真机 Edge 上量是 224。
  **识别方法只有一个：它有没有给出可复现的失败数据。**
  只讲"应该怎样"、不讲"我试了什么没成"的，基本是编的。
  这条讲出来，比任何技术细节都更能说明你有判断力。
- 别说"补环境就是伪装指纹"。补环境的本质是**复现浏览器的可观测行为**，
  不只是值。值、形状、数量、时序，四层。
- 法律边界一句话带过就够：只在授权范围、自己的靶场或明确许可的资产上做，
  不碰登录绕过的场景。

## 七、一页速查

如果只记一页，记这些数字：

```
挑战页         200 / 6058 字节
sensor         837 KB 单文件，路径 /<单词目录>/<40hex>?s=...
POST 目标      /<单词目录>/<40hex>?d=<domain>
payload        iv8 27912 / 真机 28412 / 我 34068
token          "3:..." 1258~1358 字符，renewInSec 790~890
performance    真机 46/1/7083，iv8 46/1/7442，我 597/2/630
判据           X-Iinfo 无 B 段 + 有 CT 组 = 通过
               B10 = 挑战页，B12 = 拦截
采集计数       iv8 measureText 732 / toDataURL 16 / getParameter 116
我            measureText 338 / toDataURL 12 / getParameter 58
window 属性    真机 1239，修前 292，修后 1253
toString 修复  页面执行 54.3s → 2.6s
覆盖度探针     112 项，27 项不一致（9 缺）→ 10 项（0 缺）
```

数字要能解释，不能背。面试官挑一个问"为什么是 7083"，你要能答
"那是采集过程里 `Date.now` 两次读取的差值，换成微秒算出来的"。
