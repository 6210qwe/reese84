# reese84 版本演进时间线（2022 → 2026）

> 本文汇总全网检索结果，按**时间倒序**整理 reese84 的变更史，
> 并逐条标注"对 `book.airgreenland.com` 是否成立"。
> 目的：理解 **哪些变了、哪些没变**，从而知道补环境里哪些部分需要持续维护。

---

## 0. 一句话结论

> reese84 的稳定性来自**协议不变**（GET collector → POST ?d= → token → Cookie），
> 变化全部集中在**编码层**（每日/每次重载换编码函数）和**采集项**（逐年增加、逐年细分）。
>
> ⇒ **补环境路线只要盯住"协议 + 采集面"，就不用每次重建；
> 纯算路线必须每次重建。**

## 1. 时间线（倒序）

### 2026-10 — 当前（本项目实测）

| 项 | 值 |
|---|---|
| 挑战页 | 6058 字节，HTTP **200**（不是 403） |
| sensor | 837524 字节（曾见 831750 / 838793 / 839317），单文件 |
| sensor 路径 | `/ieze-Buddieu-to-formes-from-our-he-bene-euer-The/<40位hex>?s=<8位>`，**会轮换** |
| token | `3:...`，**1290~1358** 字符，5 段 + 尾空 |
| renewInSec | **790~890**（实测 715/791/867/890 都见过） |
| 采集函数数 | 约 **22** 个（52pojie 2025-09 也是 22 个，说明半年内未变） |
| PoW | **未开启**（没有 `{"f":"gpc"}` 分支） |
| payload `p` | 24600~32816 字符 |

**新发现（2026-10 本项目）**：`performance` 字段的三个数字 **100% 来自 `Date.now()` 差值**，
与 `performance.now()` 无关。详见 `docs/02`。

### 2025-09 — 52pojie《某航司 Reese84 逆向分析-补环境篇》

来源：<https://www.52pojie.cn/thread-2062377-1-1.html>（同靶站是同类型航司）

**这篇是本项目最有价值的对照材料**，因为它逐条列出了 22 个采集函数在查什么：

| 函数 | 校验内容 |
|---|---|
| 一 | `document.addEventListener` 添加大量监听事件 |
| 二 | `window.*` 系列 |
| 十六 | 随机数组生成字符串 |
| 十七 | 向 `nt` 数组 push 一个 `true` |
| 十八 | `WebAssembly` / `window.BigInt` |
| 十九 | `document.createElement` / `navigator` 属性 / `new window.Audio()` |
| **二十** | **`Function.prototype.toString` / `call` / `apply` / `bind` 的原型链** |
| **二十一** | **`window.performance.now()` / `window.Object.getPrototypeOf()` 的属性** |
| 二十二 | 生成 `p` 值 |

**执行结构（关键）**：

```
re 数组 push 22 个函数
  → QN 方法遍历执行
  → 每个函数往 nt 数组里塞采集结果
  → 最后一个函数：p = encrypt(nt)
  → 加密前会 createElement('iframe') + 绑定 load 事件监听
```

**两条补法**（该文实测，都可行）：

1. **只取第一部分代码**，手动构造 `interrogate` + 包含 `aih` 的参数（**注意是异步函数**）
2. **一二三部分全要**，不构造 `interrogate`，只要 hook 到 `fetch` 做处理即可

> 两种方式要补的环境差不多，第二种稍多一点。该文作者"补了差不多 1 千行代码"。

**该文的坑位**：
- `window["Function"]["prototype"]["toString"]["toString"]`
- `window["Function"]["prototype"]["call"]["toString"]`
- **`window["Object"]["getOwnPropertyNames"]` 必须只返回 `['length','name']`**（作者说"第一次见"）
- iframe 里 `contentWindow` 的检测
- canvas 创建多次要注意**顺序**
- `window.OfflineAudioContext` 要真的能算出数值
- **因为 JS 是异步执行的，作者是 Python 执行 JS 后把参数写本地文件再读取**

⇒ 本项目据此补了 `nativeClass` + `__hardenPrototypeChain`，把二十多个 class 构造器和
`Function.prototype.toString/call/apply/bind` 全部伪装成 `[native code]`，
并让 `getOwnPropertyNames(函数)` 只返回 `['length','name']`（保留 `prototype`）。
**修完后页面执行时间从 54 秒降到 2.6 秒**（说明之前有分支在慢路径上跑）。

### 2025 — Hyper Solutions 接口文档

来源：<https://docs.justhyped.dev/incapsula/reese84-dynamic>

- 分 **static / dynamic** 两个变体
- 只有 dynamic 会出现 `Pardon Our Interruption`，**可能**多一步 PoW（`{"f":"gpc"}`）
- `?d=` 响应固定三字段：`token` / `renewInSec` / `cookieDomain`
- token 前缀 `3:`
- **SDK 把 `userAgent` 和 payload 一起返回，且要求回放时用同一 UA** → UA 与 payload 是绑定校验的

⇒ 对本例：dynamic 变体 ✅，**但没开 PoW**（省一步），三字段 ✅。

### 2024 — bottingrocks / BottingRocks 的生成器

- reese84 指纹编码用 **xorshift128**，每个 key-value 还经过一串 for/while 循环
  "shuffle / copy / clone / re-arrange"
- 给出了 `___utmvc` 的检测项样例（含 `Object.keys(window).length : 9163`、`eval.toString().length : 33`）
- **载荷不能静态复现，必须用同一份加密的 reese84 文件来解码**

⇒ 对本例：`___utmvc` **不存在**（本站只有 reese84，省了第一步 cookie）。

### 2024-02 — robinjia《用补环境框架测试 inCaplusa 之 reese84》

来源：<http://program.robinjia.cc/2024/02/24/用补环境框架测试inCaplusa之reese84/>

**该文的三个关键判断**：

1. **"即便 inCaplusa 觉得有异常，也会返回这个 token，也就是说 token 不一定有效，得拿去请求了才知道对不对。"**
   ⇒ 与我们实测完全一致（**签发 ≠ 信任**）
2. **"常规的如 Canvas、WebGL、font、`window["Function"]["prototype"]["toString"]`、`window["Function"]["prototype"]["call"]` 等检测"**
   ⇒ 2024 年就已经在查原型链了
3. **"拿这个网站的代码去测试其它网站，发现过不去"** —— 每个站校验严格程度不同

### 2023 — yoghurtbot 系列（utmvc 反混淆）

- 详细拆解 obfuscator.io 的 string-array、magic-number shuffle、RC4 accessor
- **该套 RC4 + shuffle 同时用于 `___utmvc` 和 `reese84` 家族**

### 2022-11 — PZz0203/Incapsula（最早的完整生成器）

来源：<https://github.com/PZz0203/Incapsula>

**该仓库给出了一个本项目之前不知道的事实**：

> The files served by Incapsula are inherently dynamic, in part because they morphed their
> encoding functions to make a slight variant of the previous one,
> **so each reload produces a different encoding function.**
> This is evident in the encoding function used for the `reese84` payload
> and the encoding function used to encode the `___utmvc` cookie.

⇒ **编码函数不是"每个 build 变"，而是"每次重载都变"**。
这解释了为什么 iv8 / 补环境能一直用（它们不碰编码），而纯算必须每次重抓。

它还提供了 `decodePayload(p, cr)` —— **`cr` 就是解码密钥**，这解释了 `cr` 字段的用途。

## 2. 什么变了，什么没变

### 2.1 变了（需要持续跟进）

| 项 | 变化频率 | 影响 |
|---|---|---|
| sensor 内容 | 每次重载（编码函数微调） | 纯算路线必须每次重建；补环境不受影响 |
| sensor 路径 | 每次挑战（40位hex 会换） | **不要硬编码**，每次从挑战页现取 |
| `?s=` 参数 | 每次请求 | 同上 |
| 采集项数量 | 逐年增加（19→20→22） | 补环境要补的面越来越大 |
| token 长度 | 随采集量浮动 | 不要按长度判成败 |
| `renewInSec` | 每次不同（715~890） | **不要硬编码 15 分钟** |

### 2.2 没变（协议层，可以固化）

| 项 | 从 2022 到现在 |
|---|---|
| 流程 | `GET 挑战页 → GET sensor → POST 同路径?d=domain → token → Cookie` ✅ |
| `Content-Type` | `text/plain; charset=utf-8`（规避 CORS 预检）✅ |
| 请求体字段 | `solution.interrogation.{p,st,sr,cr,og}` + `old_token` + `error` + `errors` + `performance` ✅ |
| 响应字段 | `token` / `renewInSec` / `cookieDomain` ✅ |
| token 结构 | `版本:段1:段2:段3:段4:` （以 `:` 结尾）✅ |
| `___utmvc` | 与 reese84 是**两套**，有的站只有 reese84 ✅ |
| 编码算法族 | xorshift128 字节重排 + RC4 字符串表 ✅ |

⇒ **"reese84 每次更新仍保证稳定性"的本质就是：协议层冻结，编码层轮换。**
这也决定了策略：**能跑原始 JS 就跑原始 JS，永远不要追编码层。**

## 3. 之前我哪里判断错了（自查）

| 早期判断 | 实际 | 依据 |
|---|---|---|
| `__utmvc` 是必需的前置 cookie | **本站没有** | 实测挑战页里无 `___utmvc` 相关 |
| `performance` 三个数字来自 `performance.now()` | **来自 `Date.now()` 差值** | `--date-scale` 有效、`--perf-scale` 无效 |
| 两个哈希键是 User Timing measure 的哈希 | **mark/measure 从未被调用** | iv8 插桩计数为 0 |
| `getEntriesByType('navigation')` 参与计时 | iv8 返回空数组也能过 | 同上 |
| cURL 的 TLS 指纹是决定性的 | **iv8 全程用 curl 也通过** | 同 IP 同时段对照 |
| `Object.keys(window).length` 应该 9000+ | **真实 Edge 是 224** | CDP 实测 |
| class 构造器不需要伪装 toString | **必须伪装**，否则源码全泄漏 | `docs/08` |
