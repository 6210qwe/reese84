# 十二条静默失败坑 —— 逐条复现与修复

> 这些坑的共同特征：**没有异常、没有日志、拿不到 token**。
> 每一个都真实耗掉了一整轮排查。按踩到的顺序排列。

---

## 坑 1：curl 加了 `--compressed` → 挑战页变 404

### 现象

```
GET https://book.airgreenland.com/api/
→ HTTP 404, 9 字节 "Not Found"
```

### 原因

本站按**请求意图**分流。`--compressed` 会带出 `Accept-Encoding`，
带着它来的请求被当成"正常导航"直接放行，不再下发挑战。

| 请求头 | 结果 |
|---|---|
| `UA` + `Accept: */*` | **200 挑战页** |
| 上面再加 `Accept-Language` | 404 放行 |
| 上面再加 `Accept-Encoding` | 404 放行 |

### 修法

```js
// bridge.js
const args = ['-sS', '-D', hdrFile, '-o', outFile, ...];
if (opts.compress) args.splice(1, 0, '--compressed');   // 默认不加
```

**反直觉点**：想拿 cookie 反而不能补全请求头。

## 坑 2：sensor 残包 → VM 静默不初始化

### 现象

没有异常、没有日志、`__body_full` 为空。比"补丁没生效"还难查。

### 原因

837KB 走国际链路经常拿不全。实测拿到过 **523984** / **695908** 字节的残包。

### 修法

```js
function sensorLooksComplete(code) {
  if (!code || code.length < 700000) return false;
  const tail = code.replace(/\s+$/, '');
  return tail.endsWith('return a1_0xdc94();}');
}
// 不完整就重下，最多 4 次；完整了缓存起来（内容对同一 build 恒定）
```

加了这条之后成功率从 ~50% 到 100%。当前 build 稳定在 **837524** 字节。

## 坑 3：`window` 用独立对象冒充 → ReferenceError

### 现象

```
ReferenceError: navigator is not defined
```

### 原因

浏览器里 `window === globalThis`。sensor 大量直接写 `navigator.x` / `document.x`，
**不用** `window.navigator.x`。用一个 `new EventTarget()` 冒充 window，这些裸访问全挂。

### 修法

```js
const __window = globalThis;
for (const m of ['addEventListener', 'removeEventListener', 'dispatchEvent']) {
  defValue(__window, m, nativeLike(EventTarget.prototype[m], m), false);
}
```

## 坑 4：内联脚本用直接 eval → `const` 跨脚本不可见

### 现象

```
ReferenceError: isSpa is not defined
```

### 原因

挑战页 4 段内联脚本共享**同一个全局词法作用域**（`const isSpa` 在第二段可见）。
直接 `eval(code)` 的作用域是当前函数，`const` 出不去。

### 修法

```js
(0, eval)(code);   // 间接 eval：落在全局作用域
```

**连带要求**：`URL` / `URLSearchParams` / `fetch` / `XMLHttpRequest` **必须定义在 window 上**，
闭包变量对间接 eval 不可见。（我第一版把 `URLSearchParams` 放在闭包里，直接 `URLSearchParams is not defined`。）

## 坑 5：`documentElement.innerHTML` 装配页面 → sensor 找不到自己

### 现象

```
Unable to find a challenge script with `src` attribute `/ieze-Buddieu...`
```

而且**不抛异常**，sensor 静默退出，永远不发 POST。

### 原因

`innerHTML` 会重建子树，但 `document.head` / `document.body` 仍指向**被替换掉的旧节点**。
于是：

```js
document.head.appendChild(script)   // 挂到了游离节点
```

sensor 随后在自己的 document 里找那个 `<script src>` —— 找不到。

这是一个非常隐蔽的"引用不同步"问题：元素明明 append 了，但不在文档树里。

### 修法

```js
function __rebuildDocument(cleanHtml) {
  const nodes = __parseHtml(cleanHtml, __document);
  let htmlEl = /* 取 <html> 或新建 */;
  st(__document).childNodes = [htmlEl];
  st(htmlEl).parentNode = __document;
  // 显式重新绑定三个关键引用
  st(__document).documentElement = htmlEl;
  st(__document).head = head;
  st(__document).body = body;
}
```

### 诊断方法

在 `__runExternalScript` 里打印可见脚本列表，一眼就能看出来：

```
脚本可见性: document.scripts(0) = []   ← 装完是 0，说明 head 引用断了
脚本可见性: document.scripts(1) = ["/ieze-Buddieu...?s=..."]   ← 正常
```

## 坑 6：`appendChild` 和 `insertBefore` 都挂钩 → sensor 跑两次

### 现象

payload 明显偏小，且行为不稳定。

### 原因

```js
// lib/internal 里的实际实现就是这个
Node.prototype.appendChild = function (child) {
  return this.insertBefore(child, null);
};
```

两个都挂 → 同一个 script 被执行两次 → 第一次采集的副作用污染第二次。

### 修法

**只挂 `insertBefore`。**

## 坑 7：iframe 的 `load` 永远不会来

### 现象

VM 静默卡住，不发 POST。用 `addEventListener` 钩子能看到它停在：

```
createElement → IFRAME
IFRAME   | addEventListener load      ← 卡这里
```

### 原因

sensor `createElement('iframe')` → 设 name → **不设 src** → 注册 `load` 监听 → 等。
补环境没有浏览上下文，`load` 不会自己触发。

### 修法

```js
// insertBefore 钩子里
} else if (tag === 'IFRAME') {
  __HOST__.setTimeout(() => {
    try { child.dispatchEvent(new Event('load')); } catch (e) {}
  }, 20);   // 20ms 足够等到监听器注册完成
}
```

## 坑 8：`__installCtx2D` / `__installGL` 定义了忘记调用 ★ 卡最久

### 现象

- payload 从 32KB 掉到 20KB
- `canvas.create` 计数正常（9 次），但 `canvas.create` 后端一次没初始化
- `performance.total` 只有几百微秒
- **服务端返回 400，body 为空**

### 原因

```js
function __installCtx2D(proto) { /* 装属性与方法 */ }
function __installGL(proto, isGL2) { /* ... */ }

// ← 文件末尾忘了调用！
```

结果 `CanvasRenderingContext2D.prototype` 上只剩构造函数，
sensor 的能力探测（读 `ctx.rect` / `ctx.fillRect` / `ctx.measureText`）**全部拿到 `undefined`**
→ 它静默跳过 canvas 采集。

### 诊断方法

用 Proxy 包一层 ctx，记录所有属性访问：

```js
// --trace-ctx
ctx 操作轨迹: ["ctx.get.rect","ctx.set.globalAlpha","ctx.set.fillStyle",
              "ctx.get.fillRect","ctx.set.font","ctx.get.measureText"]
```

**有操作轨迹，但 `canvas.create` 计数为 0** —— 这两个信号放在一起就能定位：
**它在访问，但访问的是空壳，所以走不到真实后端。**

### 修法

```js
// 文件末尾
__installCtx2D(CanvasRenderingContext2D.prototype);
__installGL(WebGLRenderingContext.prototype, false);
__installGL(WebGL2RenderingContext.prototype, true);
```

修完 payload 立刻从 20604 → 32816，canvas 后端 18 次、measureText 338 次。

## 坑 9：`&nbsp;` 被 `trim()` 吃掉 → 被判定"装了 adblock" ★ 最阴

### 现象

和坑 8 极其相似：canvas 后端一次没建、payload 少 30%、`performance.total` 只有几百微秒。

### 原因

reese84 的**广告拦截检测**会造一个诱饵 div 塞进 body：

```js
bait.innerHTML = '&nbsp;';          // 实际是 \u00a0
// 然后读 offsetHeight / offsetWidth / clientHeight / clientWidth
// 全 0 → 判定"这个环境装了 adblock" → 整段指纹采集被跳过
```

而我们的布局计算里：

```js
const txt = (el.textContent || '').trim();
if (txt) acc = Math.max(acc, 17);   // ← trim() 把 \u00a0 也裁掉了
```

验证：

```js
'\u00a0'.trim() === ''    // true
```

`String.prototype.trim()` 会裁掉 `\u00a0`（NBSP）。所以诱饵高度算成 0。

### 修法

```js
const raw = el.textContent || '';
if (raw.length > 0) acc = Math.max(acc, 17 * Math.ceil(raw.length / 60));
// 有子元素但没算出高度时给最小可见高度，避免"内容存在却高 0"
if (h === 0 && kids.length > 0) h = 17;
```

**判"元素有没有内容"永远用 `length > 0`，不要用 `trim()`。**

## 坑 10：`setPrototypeOf(globalThis, Window.prototype)` → 408 Timeout

### 现象

```
[5] 页面执行结束 (99454ms)
POST → 408 Timeout
```

（正常情况下页面执行约 58 秒，加上这个变成 99 秒。）

### 原因

`Object.setPrototypeOf(globalThis, ...)` 让 V8 **放弃全局对象的内联缓存**，
之后每一次 window 属性访问都走慢路径。sensor 里 window 属性访问是十万量级的。

页面执行被拖到 99 秒后，服务端的 `?d=` 会话窗口过期，返回 **408 Timeout**（body 7 字节 `Timeout`）。

### 修法

默认关闭，只在需要 `instanceof Window` 时用 `--window-proto` 打开：

```js
if (__CFG.windowProto) {
  try { Object.setPrototypeOf(__window, Window.prototype); } catch (e) {}
}
```

## 坑 11：`performance.now()` 全精度 → 一眼假

### 现象

500 次连续调用返回 500 个不同值。

### 原因

Chrome 为防 Spectre 会降低 `performance.now()` 精度。实测本机 Edge：

```
500 次连续调用 → 只有 4 个不同值
```

我们直接返回 `hrtime` 的纳秒级浮点 → 500 个不同值。这是任何脚本都能测出来的"非浏览器"特征。

### 修法

```js
now() {
  const t = Number(process.hrtime.bigint()) / 1e6 - t0ms;
  return Math.round(t * 10) / 10;   // 量化到 0.1ms
}
```

**并且绝不能依赖 `this`**：

```js
// ✗ 错误：sensor 是 `new TimerFactory(performance.now)`，解构后 this 丢失
now() { this.__calls++; ... }

// ✓ 正确：统计放闭包
now() { nowCalls++; ... }
```

`this` 丢失会抛错 → sensor 捕获后退回 Date 计时分支 → `performance.now` 调用次数变成 0。

## 坑 12：硬件值靠猜 → 自相矛盾

### 实测本机真实值 vs 我猜的值

| 项 | 我猜的 | 本机真实 | 后果 |
|---|---|---|---|
| `hardwareConcurrency` | 8 | **16** | 与设备等级矛盾 |
| `screen` | 1536×864 | **1366×768** | 与 `innerWidth/outerWidth` 矛盾 |
| `deviceMemory` | 8 | **undefined** | Chrome 141 已不暴露，写了反而是破绽 |
| WebGL renderer | `ANGLE (AMD, AMD Radeon(TM) Graphics Direct3D11 vs_5_0 ps_5_0, D3D11)` | `ANGLE (AMD, AMD Radeon (TM) Graphics (0x00001900) Direct3D11 vs_5_0 ps_5_0, D3D11)` | 少型号 id，属自造指纹 |

### 修法

全部走真实采样（`tools/sample_fp.js`），且采样时**不要 `--disable-gpu`**：

```js
// ✗ 会让 WebGL 报 "Microsoft Basic Render Driver"，与真实显卡矛盾
'--disable-gpu'

// ✓
'--enable-gpu', '--use-angle=d3d11'
```

### 相关：generic 字体度量

用 CDP 的 `CSS.getPlatformFontsForNode` 拿到权威答案：

| generic 族 | 本机实际解析成 |
|---|---|
| `sans-serif` | **Noto Sans SC** |
| `serif` | **Noto Serif SC** |
| `monospace` | **NSimSun** |
| `system-ui` | **Microsoft YaHei UI** |

同一字体 `Noto Sans SC`：Chrome 10px 量得 **101.03**，Skia 量得 **96.43**（差 4.6%）。
显式族名（`Arial` 125.95 / `Times New Roman` 137.79）两边**完全一致**，只有 generic 族不一致。

⇒ 服务端如果校验"字体存在性与度量一致性"，这是可查的破绽。

## 附：排查这些坑的通用工具

| 症状 | 用哪个开关 |
|---|---|
| 完全没反应、不发 POST | `-v` 看 env 日志；`diag` 看请求记录 |
| 怀疑 ctx/API 是空壳 | `--trace-ctx`（记录每个属性/方法访问） |
| 怀疑 sensor 读了什么 | `--trace-timing`、`--trace-stack` |
| 怀疑资源是残包 | `--fresh` 强制重下 + 看 `len` |
| 怀疑服务端要什么 | 去 iv8 里插桩（`iv8/probe_iv8_perf.py`） |
| 怀疑指纹不一致 | `tools/probe_fp_env.js` 逐项打表 |
