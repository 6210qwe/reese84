# `performance` 计时之谜 —— 完整排查记录

> 这是本仓库最核心的一篇。记录"我们和能通过的 iv8 之间，唯一还没解释的差异"，
> 以及 7 个被逐一排除的假设。给后来者省掉重复实验。

---

## 1. 差异是什么

payload 里 `performance` 字段（同一时段、同一出口 IP）：

| 方案 | `["1030820235"]` | `["4203433130"]` | `total` | 回放 |
|---|---|---|---|---|
| 真实浏览器 | 46 | 1 | **7083** | ✅ |
| iv8 | 46 / 47 | 1 | **7442 / 6570** | ✅ |
| 本方案 | 459~678 | 0~2 | **484~710** | ❌ B12 |
| jsdom | 446 | 2 | 465 | ❌ |

两个哈希键（`1030820235` / `4203433130`）推测是 User Timing measure 名字的哈希，
值是 duration；`total` 是总耗时。

**关键观察：我们的 `total` 比真机小 12~14 倍。**

---

## 2. 第一步：去"能通过的实现"里拿基准

在自己失败的环境里猜服务端要什么，永远是猜。所以先给 iv8 插桩。

`iv8/probe_iv8_perf.py` 做的事：把 `PERF_HOOK` 拼在
`reese84_iv8_hooks.js` 和 837KB VM **之间**，一起注入 `resources`（因为 `page.load` 会重置 window，
补丁必须 prepend 到 VM 源码前）。

### 实测输出

```
    performance = {"1030820235": 47, "4203433130": 1, "total": 6570}
    now 调用 8008 次，跨度 6534.136 ms；Date.now 调用 21 次

    --- performance 轨迹（7 条）---
      INFO                    perf keys               0
      query:getEntriesByType  navigation              0  len=0
      INFO                    navigation entries      0  len=0 dur=undefined
      query:getEntriesByType  navigation              0  len=0     ×4
```

### 由此确定的三件事

1. **`performance.now()` 被调用 8008 次，跨度 6534ms** —— 与 `total=6570` 同量级
2. **`mark` / `measure` 一次都没被调用** —— 不是 User Timing
3. **`getEntriesByType('navigation')` 返回空数组** —— iv8 也没有 Navigation Timing，照样通过

第 2 点推翻了我最初的判断（以为那两个键来自 measure），第 3 点说明 Navigation Timing 不是必需项。

---

## 3. 七个被排除的假设

### 假设 1：`total` = `performance.now()` 的跨度

**看起来最像**：iv8 跨度 6534ms → total 6570（差 36）；我们跨度 470~620ms → total 492~661（差 20~40）。

**证伪实验**：给 `now()` 返回值乘缩放系数（虚拟时钟）。

```
--clock-scale 13  →  total 575   （跨度记录用的是真实值，未缩放）
--clock-scale 14  →  total 558
```

**结论：❌ `total` 不来自 `performance.now()` 返回值。**

### 假设 2：`total` = `now()` 调用的真实耗时（spin 能拉长）

**证伪实验**：在 `now()` 里加真实自旋。

```
--now-spin 200   →  total 510   跨度 478ms / 22 次
--now-spin 600   →  total 544   跨度 516ms / 15 次
--now-spin 1500  →  total 492   跨度 470ms / 12 次
```

**结论：❌ 无效。** 两个副作用值得记：
- 首尾调用同步后移，**跨度不变**（所以"用 spin 拉长采集耗时"这个思路从根上不成立）
- 调用次数从 78 掉到 12 —— 说明传感器有**时间预算逻辑**，跑得慢就跳过步骤

### 假设 3：`total` = `performance.timing` 的字段差

**追踪结果**（`--trace-timing`）：sensor 读了 `performance.timing`，但**只读了 `navigationStart` 一个字段**。

**证伪实验**：把 `navigationStart` 提前 60 秒。

```
--nav-offset 0      →  total 549
--nav-offset 60000  →  total 546
```

**结论：❌ 不来自 timing 差值。** `navigationStart` 拿去做校时/校验，不参与 total 计算。

### 假设 4：`total` 来自 `getEntriesByType('navigation')`

**证伪**：iv8 返回空数组也能通过，我们也返回（更真实的）entry，`total` 没变。
另外补上完整 `PerformanceNavigationTiming` 前后，`total` 从 484 变 507（噪声级）。

**结论：❌。**

### 假设 5：`total` 来自 User Timing（`mark`/`measure`）

**证伪**：iv8 里 `mark`/`measure` **调用次数为 0**；我们环境里也只有一次
`getEntriesByType('navigation')` 的查询。追踪器全程没记录到 measure。

**结论：❌ 不是 User Timing（最初判断错误，已纠正）。**

### 假设 6：`total` 来自 `Date.now()`

**证伪**：`Date.now()` 调用次数约 21 次（iv8 也是 21 次），覆盖不了 6 秒的采集过程。
另外 `Date.now` 精度是 1ms，而 `total` 是 500~7442 这种非整千的值。

**结论：❌。**

### 假设 7：`total` 来自 `new Date().getTime()/valueOf()`

**证伪**：patch 了 `Date.prototype.getTime` / `valueOf` 统计，`total` 无变化（619 量级）。

**结论：❌。**

## 4. 当前判断与下一步

### 4.1 判断（诚实标注"未验证"）

- `total` 极可能**确实是"整段采集的真实耗时"**，只是用了我们还没探到的时间源
  （或者是一个 VM 内部的计数器，比如"处理了多少个字段 × 单字段权重"）。
- 12 倍的差距来自**物理事实**：
  **纯 JS 的 DOM 属性访问比 Blink 的 binding 层快一个数量级。**
  iv8 走 C++ 绑定层（慢，接近真机），我们走 JS 对象属性（快，露馅）。
- crawlex 的说法与此一致：这是 band 检测，"便宜采集、昂贵伪造"。

### 4.2 ★ 下一步：用"可识别偏移"一次性定位时间源

**这是我最推荐的下一步，因为它能在一次运行内定位所有时间源。**

思路：把 window 上**所有能返回时间的东西**各加一个**互不相同的**偏移量，跑一次，
看 `total` 变了多少 —— 变了多少就知道用的是哪个。

```js
// 在补环境里执行（sensor 之前）
const MARKS = {
  perfNow:     +1,        // performance.now()
  dateNow:     +2,        // Date.now()
  dateGetTime: +4,        // new Date().getTime()
  dateValueOf: +8,        // +new Date()
  timeOrigin:  +16,       // performance.timeOrigin
  navStart:    +32,       // performance.timing.navigationStart
  evTimeStamp: +64,       // new Event('').timeStamp
  rafArg:      +128,      // requestAnimationFrame(cb) 的 cb 参数
  perfTimingX: +256,      // timing 的其余字段
};
```

跑一次，看 `total` 增加了 1 / 2 / 4 / … 中的哪个 → 直接命中。

如果**全部加上之后 `total` 仍不变**，那它就是 VM 内部计数器（与任何外部时间源无关），
这条路可以彻底放弃，转 §4.3。

### 4.3 备选：让环境访问真实变慢

给高频 API 加固定微秒成本，把采集墙钟从 0.5 秒拉到 6~7 秒：

| 目标 API | 现状（纯 JS） | 真机（Blink） |
|---|---|---|
| `offsetWidth` / `offsetHeight` | ~0.1 μs | 数 μs |
| `getBoundingClientRect` | ~0.5 μs | 10~20 μs |
| `getComputedStyle` | ~1 μs | 30~50 μs |
| `navigator.*` | ~0.1 μs | 1~2 μs |
| `canvas.measureText` | 1~2 μs（Skia） | 5~15 μs |

风险：**可能撞 10 秒兜底**（挑战页有 `setTimeout(showBlockPage, 10000)`）。
实测我们页面执行本身就要 60~70 秒（大头是 837KB VM 的解析执行），
如果采集再多 6 秒，需要确认仍在服务端 `?d=` 的会话窗口内
（我们曾因页面执行 99 秒而吃过 **408 Timeout**）。

### 4.4 备选：换执行层

CSDN《reese84风控绕过》选择 Rust 自研 JS 引擎 + 底层重建浏览器环境，
把"原生性"和"时钟一致性"一起解决。这说明该问题在纯 JS 层确实不好解。

---

## 5. 给后来者的三条提醒

1. **不要用 spin 拉长耗时。** 首尾同步后移，跨度不变（已实测）。
   而且会触发传感器的"时间预算"逻辑，让它跳过步骤（调用次数 78→12）。

2. **不要相信"数值接近就是同一个量"。**
   `total=6570` 与 `now 跨度 6534ms` 看起来一模一样，但缩放 `now()` 后 `total` 纹丝不动。
   必须做"改变输入 → 观察输出"的对照，而不是相关性。

3. **插桩要插在能通过的实现里。**
   在自己失败的环境里，你连"正确答案长什么样"都不知道。

# 6. 后续进展（2026-10-18 凌晨）—— 找到时间源了

上一节留下的问题是"`total` 到底用哪个时间源"。这一轮把它挖出来了。

## 6.1 决定性发现：三个数字全部来自 `Date.now()`

之前所有实验都在 `performance.now()` 上打转，全部无效。**拆开测一次就清楚了**：

| 只缩放 | `phase1` | `phase2` | `total` |
|---|---|---|---|
| 基线（都不缩放） | ~500 | 1 | ~540 |
| **只缩放 `Date.now` ×12** | **8268** | **12** | **8592** |
| 只缩放 `performance.now` ×12 | 536 | 1 | 570（纹丝不动） |

**结论：`phase1` / `phase2` / `total` 三个数字全部来自 `Date.now()` 的差值，与 `performance.now()` 完全无关。**

这一条推翻了前面 7 个假设的全部前提——它们都建立在"用的是 performance.now"之上。

> 为什么前面"给 `Date.now` 加常数偏移 +2"没有变化？
> 因为常数偏移不影响**差值**。只有**缩放**（乘系数）才改变差值。

## 6.2 iv8 的 total 是"虚拟时间推进量"，不是真实耗时

在 iv8 里插桩拿到：`now 调用 8008 次，跨度 6534ms`，而 `total=6570`。
同时 iv8 的驱动代码是：

```python
for _ in range(14):
    ctx.eval("__iv8__.eventLoop.sleep(600);")   # 14 × 600ms = 8.4s 虚拟时间
```

**所以 iv8 的 `total=6570` 反映的是"虚拟时间推进了 6.5 秒"，不是它真的跑了 6.5 秒。**

这解释了为什么 iv8 能过、我们不能：sensor 是**用 setTimeout 分阶段采集**的，
每个阶段之间有真实的等待（真实浏览器 16~600ms/次，累积 6~8 秒）。
iv8 用虚拟时钟把这段等待"拨快"了；我们则是**同步 eval 一次跑完**，等待时间根本没发生。

## 6.3 用时钟跳变精确控制 total ✅

既然是 `Date.now` 的差值，就可以精确控制：

```
--clock-jump 6500   →  total = 7118   （真实浏览器 7083，iv8 6570）✅ 完美落进 band
```

但同一个跳变也让 `phase1` 变成 7090（iv8 是 46）——因为**跳变落在 phase1 的计时窗口内**。

## 6.4 phase1 的窗口覆盖整个采集，卡不进去

试了三种卡点方式，全部失败：

| 卡点方式 | 结果 |
|---|---|
| 在第一次 `canvas.toDataURL` 时跳变 | phase1 = 7090（含跳变） |
| 在第 N 次 `Date.now()` 调用后跳变（N=2 / N=4） | phase1 = 7035 / 7457（都含跳变） |
| 用 `--timer-scale 20` 让定时器虚拟时间解耦 | total=15419、phase1=15386（同步放大） |

**并且发现 `total ≈ phase1 + 28μs`**（886/921、657/689、503/540、1294/1346），
说明 phase1 就是 total 的主体。而 iv8 是 `total - phase1 = 6524μs` —— 那 6.5 秒在 phase1 窗口**之外**。

⇒ **我们的 sensor 走的是"同步一次性采集"路径，phase1 自然包住全部；
iv8 / 真实浏览器走的是"分阶段采集"路径，phase1 只包住其中一小段。**

这是**路径差异**，不是"某个值算错了"。想修就得让 sensor 也走分阶段路径。

## 6.5 采集次数对比：我们只跑了一半

在 iv8 里也插桩了采集计数，和我们的 counters 直接对比：

| 采集项 | iv8 | 本方案 | 比值 |
|---|---|---|---|
| `ctx.measureText` | 732 | 338 | 0.46 |
| `canvas.toDataURL` | 16 | 12 | 0.75 |
| `canvas.create` | 32 | 18 | 0.56 |
| `getContext.2d` | 24 | 14 | 0.58 |
| `gl.getParameter` | 116 | 58 | 0.50 |
| `ctx.getImageData` | 8 | 4 | 0.50 |
| `ctx.putImageData` | 8 | 4 | 0.50 |
| `create.audio` | 4 | 6 | 1.5 |
| `create.iframe` | 4 | 4 | 1.0 |
| **`performance.now` 调用** | **8008** | **78** | **0.01** |

**几乎每一项都精确是 iv8 的一半**（0.46~0.58），而 `performance.now` 调用差 100 倍。

"精确一半"意味着 sensor 有**两轮采集**（首轮 + 复核轮），我们只跑完了首轮就提交了。

## 6.6 结论与下一步

**已经确认的**：

1. `performance` 的三个数字 **100% 来自 `Date.now()` 差值**（这是本条最重要的可复用结论）
2. 用 `--clock-jump` 可以**精确**把 `total` 调到任意值（已验证 7118，落进真机 band）
3. iv8 的 `total` 是**虚拟时间推进量**，不是真实耗时 —— 所以"让环境变慢"这条路从根上是错的
4. 我们和 iv8 的差异是**执行路径**：我们是"同步一次性采集"，iv8/真机是"分阶段采集 + 每阶段真等待"
5. 我们的采集次数是 iv8 的约 **一半**，说明只跑完了首轮

**下一步（按可行性排序）**：

1. **找出"第二轮采集"的触发条件**。既然计数精确是一半，就一定能定位到某个分支没进去。
   最快的办法：在 iv8 里计数 `setTimeout` 的 delay 分布与回调次序，
   对比我们的执行次序，找出第二轮的第一个动作。
2. **让 sensor 走分阶段路径**。现在的 `<script>` 是同步 `eval` 一次性执行；
   真实浏览器里 sensor 的动态 `<script src>` 也是同步的，但**它内部用 setTimeout 排阶段**。
   如果我们的 setTimeout 真的按顺序、按延迟触发（而不是同步跑完），
   路径可能自然就对了。
3. 检查 `onProtectionInitialized` / `cookieIsSet()` 分支。
   如果 sensor 认为"已经完成"，它可能就不做第二轮复核。

**明确不要再做的**：

- ✗ 缩放 / 加自旋 `performance.now()`（无效，不是它）
- ✗ 给 `Date.now` 加常数偏移（差值不变）
- ✗ 用 `--slow-dom` 让环境变慢（total 反而变小，且触发时间预算跳过步骤）

## 6.7 补测：那"一半缺失的采集"不是没等到，是被取消了

按 §6.6 第 1 条去查 timer，加了注册/触发/取消三个计数的追踪：

```
timer 最终：注册 65 / 触发 30 / 取消 37（未触发且未取消 -2）
delay 分布: {"0":26, "1":1, "100":32, "200":1, "300":1, "400":1, "10000":2}
```

**35 个未触发的 timer 全部被 sensor 自己 `clearTimeout` 掉了**（备选路径，条件满足即取消）。

⇒ "两轮采集、我们只跑完首轮"这个假设**不成立**。sensor 就是只跑一轮。

并且即使把等待拉长到 20 秒（`--settle 20000`），timer 触发数也不再增加（30 → 30），
报文里也始终只有 **1 个 POST**。

所以 §6.5 里"计数精确是一半"更可能的解释是：
**iv8 的 8.4 秒虚拟时间推进让 sensor 的多个异步分支都有机会执行，
而我们的同步执行在 0.5 秒内就收敛了** —— 差异在"异步机会"的多少，不在分支逻辑。

## 6.8 本轮净收获（可复用的部分）

| 结论 | 价值 |
|---|---|
| **`performance` 三个数字 100% 来自 `Date.now()` 差值** | ★★★ 最高。一条推翻前面所有假设的前提 |
| `--clock-jump` 可精确把 `total` 调到任意值（已验证 7118） | ★★★ 工具可用 |
| iv8 的 `total` 是虚拟时间推进量，不是真实耗时 | ★★ 纠正认知方向 |
| timer 注册/触发/取消三计数（64/28/37） | ★★ 诊断手段，一分钟看清异步路径 |
| iv8 侧采集计数（measureText 732 / toDataURL 16 / gl.getParameter 116） | ★★ 提供了"目标值" |

**尚未解决的**：`phase1` 与 `total` 的比例。
我们的 `total = phase1 + 28μs`，iv8 是 `total - phase1 = 6524μs`。
因为 phase1 的窗口覆盖整个同步采集期，任何时刻跳变都会落在里面，
所以**无法在保持 phase1 小的同时把 total 做大**。

⇒ 结论：**要在纯同步执行模型下同时满足这两个数字，可能本来就不可行。**
这也间接解释了为什么 CSDN 那篇选择自研 JS 引擎（可以精确控制虚拟时钟与异步调度）
而不是在 Node 里补环境。
