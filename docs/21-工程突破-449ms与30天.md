# 工程突破：求解 449ms、有效 30 天

这一轮没能让补环境通过，但把**可用方案的性能提升了一个数量级**。
两个发现都来自同一个错误的修正。

---

## 一、修正的错误：有效期算错了 99%

我一直按 `renewInSec`（790~890 秒）过滤 token，认为它 12~15 分钟就失效。
于是 token 池的逻辑是"快过期的提前续"，导致实际使用中要频繁重新求解。

**错在哪：** `renewInSec` 只是服务端建议的"主动续期间隔"，
不代表 token 到时就失效。真正的有效期看 cookie 自身的 `expires`。

从 CDP 的 `Network.getAllCookies` 读出来：

```
reese84 cookie expires = 2026-11-16T20:48:30Z
当前时间              = 2026-10-18T04:50Z
有效期                ≈ 30 天
```

**30 天，不是 13 分钟。** 我把可用期砍掉了 99%。

---

## 二、意外收获：持久化 profile 让求解快 25 倍

原来是每次求解开一个新 profile（`--user-data-dir=/tmp/r84pool-<pid>-<ts>`），
用完就删。理由写得挺像那么回事："避免累积占用磁盘"。

改成复用同一个 profile 之后：

| 配置 | 求解耗时 | 说明 |
|---|---|---|
| 新 profile（冷） | **11326 ms** | 每次都要重新 TLS 握手、下载 837KB sensor、跑完整挑战 |
| 复用 profile（热） | **449 ms** | TLS 会话、脚本缓存、cookie 都还在 |
| ~~上一版的池（新 profile + 12 分钟失效）~~ | ~~9976 ms / 12 分钟~~ | 相当于每 12 分钟付 10 秒 |

**25 倍差距**，而且省了 837KB 流量。

热启动时服务端基本不再下发挑战，直接认 cookie —— 这本身就是"这个客户端之前来过"的信用。

### 验证

```
=== 第 1 次（持久化 profile，冷） ===
  耗时 11326ms  token 1354  剩余 30.0 天
=== 第 2 次（同一持久化 profile） ===
  耗时 449ms    token 1354  剩余 30.0 天

=== 验证第 2 次的 cookie 能否通过 ===
  HTTP=302 len=213 被拦=false
  X-Iinfo: 53-295704284-295704700 NNNN CT(262 264 0) RT(...) q(0 0 5 -1) r(8 ...)
  判定: ✅ 通过（无 B 段 + 有 CT 组 + q(0 0 5 -1)）
```

## 三、成本重算

按新的数据：

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 单次求解 | 10 秒 | 0.45 秒（热） |
| token 可用期 | 12 分钟 | **30 天** |
| 30 天内的求解次数 | ~3600 次 | **1 次** |
| 30 天总耗时 | ~10 小时 | **11 秒** |

也就是说：**开局花 11 秒，之后一个月不用管。**

这比"攻通补环境"的实际收益还大 —— 补环境再快也不可能比"根本不用解"快。

## 四、这一轮还补了一个真实缺口

搜索到 CSDN 一篇《JS逆向 - Reese84-SilverFlume 补环境》提到：
`Uint8Array.prototype.toBase64` 在 Node 25 才有，低版本要自己补。

核实（真实 Edge vs 我们的 Node 22）：

| API | 真实 Edge | Node 22 |
|---|---|---|
| `Uint8Array.prototype.toBase64` | function | **undefined** |
| `Uint8Array.prototype.toHex` | function | **undefined** |
| `Uint8Array.fromBase64` | function | **undefined** |
| `Uint8Array.fromHex` | function | **undefined** |
| `ArrayBuffer.prototype.transfer` | function | function |

**前四个全缺。** 这是 2024 年进标准、Chromium 早已支持的一组方法。
sensor 如果用它编码（比手写 base64+btoa 快），我们环境里会抛 TypeError 被吞掉。

已在 `01-core.js` 里补上 `toBase64 / toHex / fromBase64 / fromHex / setFromBase64 / setFromHex`，
顺带补了 `ArrayBuffer.prototype.transferToFixedLength`。

补完之后 payload 从 24232 变成 23760（有变化，说明确实被用到了），但仍 B12。

**这类"新标准 API 缺失"是最难发现的**：所有补环境 checklist 都是 2020 年写的，
不会包含 2024 年的 API。以后应该直接从真实浏览器 dump 一份
"所有构造器 prototype 上的方法名"，做差集，而不是靠别人的清单。

## 五、虚拟定时器：试了，不可行

按 iv8 的 `for _ in range(14): eventLoop.sleep(600)` 实现了虚拟定时器队列：
`--virtual-timers` + `--drive 14`，可以手动推进虚拟时间。

结果：**sensor 完全不发 POST**（等到 121 秒也没有）。

原因：真实定时器模式下 sensor 的异步链路能自然推进，
换成虚拟队列后，它注册的回调排队但不执行，链路断了。
而 `advance()` 每轮只执行 1 个回调（第 1 轮）之后就是 0 个 ——
说明它的采集主力不在 `setTimeout` 里，而在 **microtask / fetch 回调**上。

**结论：** Node 的 vm 里 microtask 是自动 flush 的（`runInContext` 返回后），
没法像 iv8 那样"暂停在某一轮"。虚拟定时器只能模拟宏任务，
模拟不了 iv8 那种"整个 event loop 由宿主驱动"的模型。

这条路走不通，代码留着（`--virtual-timers`），但默认关闭。

## 六、现在的最终方案

```bash
# 一次求解（热启动 0.45 秒）
node tools/token_pool.js

# 起服务，业务侧 HTTP 取
node tools/token_pool.js --serve 8899
curl 'http://127.0.0.1:8899/token?host=book.airgreenland.com'
→ {"token":"3:...","cookie":"...","remainingSec":2589000}
```

关键配置（都在代码里注释了）：

1. **持久化 profile**（默认开）—— 求解 11s → 0.45s
2. **有效期用 cookie expires**（30 天），不用 `renewInSec`
3. **有头模式** —— headless 拿不到 token
4. **不覆盖 UA** —— 覆盖后 UA 与 `sec-ch-ua` 矛盾，直接失败

## 七、这一轮的方法论

1. **一个错误的口径会造成数量级的浪费。**
   我把"建议续期间隔"当成"有效期"，结果每 12 分钟重解一次。
   **任何"多久失效"的判断，都要从原始数据（cookie expires）读，不要从衍生字段（renewInSec）猜。**
2. **性能问题常常藏在"我以为在优化"的代码里。**
   每次删 profile 是我为了"省磁盘"主动加的，结果它是最大的性能瓶颈。
   删掉之后快 25 倍。**优化之前先测量。**
3. **新标准 API 是补环境的盲区。**
   所有 checklist 都有时效性。应该从真实浏览器 dump 方法名做差集，不要信清单。
4. **不是所有"照抄 iv8"都能成。**
   虚拟定时器照抄的是它的 `eventLoop.sleep`，但 iv8 能做到是因为整个 event loop
   归它管；Node 的 vm 里 microtask 自动跑，没法暂停。**照抄之前先确认自己有没有那个控制权。**
