# 现状：补环境未做成，但有可用方案

写于 2026-10-18 04:20，连续跑了六轮之后。这篇只讲两件事：
**哪些还没实现、为什么**，以及**现在能用什么**。

---

## 一、还没实现的（如实列）

### 1. 纯 Node 补环境过 reese84 —— 未成功

现状：能产出服务端**签发**的 token（1254~1370 字符），但 POST 响应头带 `B12(14,0,0)`，
拿这个 token 访问业务页拿到的是拦截页。

已排除的（每一条都是实测，不是推测）：

| 假设 | 排除方式 |
|---|---|
| HTTP/TLS 指纹 | iv8 全程也用 curl，能过 |
| IP 信誉 | 同时段 iv8 能过（198987 字节真实首页） |
| canvas 编码器与 Chrome 不一致 | iv8 用自研 canvas 也能过 |
| 缺 User Timing / Navigation Timing | iv8 里插桩：mark/measure 0 次、navigation 空数组 |
| `performance.now` 快慢 | 只缩放它，payload 三个数字纹丝不动 |
| **时序形态（timing band）** | **见下，整条假设被推翻** |
| 会话 / 连接绑定 | 浏览器 body 交到我们新建的会话，照样通过 |
| 环境能力缺失 | 112 项覆盖差集，缺失从 9 降到 0 |
| 函数形状泄漏 | 80+ 构造器 toString 已修，页面执行 54s→2.6s |

### 2. 时序假设被推翻（这条最重要）

我之前拿"真机 `performance` = 46 / 7083"当靶子，调了一整天的时钟。
**那个数字是错的** —— 它来自探针量 `performance.now` 的跨度，不是 payload 字段。

从浏览器抓下来的 POST body 里读，真值是：

```
浏览器 {"1030820235": 4970, "4203433130": 0, "total": 4977}   phase1 ≈ total (99.9%)
iv8    {"1030820235": 46,   "4203433130": 1, "total": 6570}   phase1 只占 0.7%，却通过
我们   {"1030820235": 597,  "4203433130": 1, "total": 630}    phase1 占 95%
```

**浏览器的形态和我们一样，iv8 的形态和我们相反，iv8 却通过。**
⇒ 时序形态根本不参与校验。整条假设作废，为它调的
`--clock-jump` / `--date-scale` / `--warp-ms` / `--fake-start` 全部无效
（工具留着，方向是错的）。

### 3. payload 内容层面无法对齐 —— 这是走到头的标志

试过的两条路都堵死：

**路 A：固定随机数让编码一致。** 加了 `--fix-random`，我们自己的 `cr` 稳定了
（两次运行都是 519911612），但 iv8 的 `cr` 是 1015592461 ——
**两边消耗随机数的次数不同**（环境差异导致的），同种子也对不齐。

**路 B：二进制结构对齐。** 三方 payload 解 base64 后都是 `bin1` + 高熵数据：

```
iv8   22898 字节  62 69 6e 31 34 d8 9b 4d 8d ...
ours  24467 字节  62 69 6e 31 cb 8b 2b 11 bb ...
brw   28630 字节  62 69 6e 31 bb f1 23 b6 f1 ...
```

`bin1` 之后的字节被 `cr` 加密，不同会话不同。**没有任何明文锚点可以对齐。**

要把这条路走通，只剩一个办法：**在能通过的实现（iv8）里 hook 到编码前的明文对象**，
把那 38 个字段的值 dump 出来，再和我们的对比。

这需要定位 sensor 内部"38 个字段组装完、送去加密"的那个时刻。
sensor 是 JSVMP + RC4 字符串表，定位它等于逆向虚拟机。
**这是纯逆向工程量，不是补环境能绕过的。**

### 4. 字体探测差异 —— 线索作废

iv8 的 `measureText` 732 次、我们 338 次，看起来是"精确 2 倍"，很像少跑一轮采集。

加了统计之后发现**每次运行的次数本来就不固定**：我们同一份代码跑三次得到
169 / 338 / 不同值（取决于 sensor 内部走了哪条分支）。而且每个 font 声明只测 1 次，
169 种声明覆盖 169 个不同族 —— 结构是"56 个候选字体 × 3 个 generic fallback"。

⇒ "iv8 比我们多一倍"这个观察不成立，不能当判据。

## 二、现在能用的方案：token 池

`tools/token_pool.js`

### 为什么是池，而不是每次解

三条实测事实决定了设计：

1. **载荷不绑会话。** 浏览器产出的 body 提交到另一个 curl 新建的会话，照样
   `200 + token + X-Iinfo 无 B 段`。⇒ token 可以跨进程、跨连接复用。
2. **一次求解 9.5~10 秒**（有头 Edge + CDP）。
3. **服务端 `renewInSec` = 790~890 秒。** ⇒ 一个 token 能用 13~15 分钟。

9.5 秒 / 13 分钟 = 1.2% 的时间成本。所以正确用法是**后台预热、业务侧直接取**，
而不是每次请求前解一次。

### 实测数据

```
第 1 次取（冷启动）    9976 ms   token 1366 字符   剩余 720s
第 2 次取（缓存命中）     0 ms   同一个 token = true
并发 5 次取              0 ms   全部同一个 = true
```

验证（用池里的 cookie 访问 `/`）：

```
HTTP=302  len=213  被拦=false
X-Iinfo: 50-232734477-232734625 NNNN CT(253 254 0) RT(...) q(0 0 5 -1) r(8 8) U11
判定: ✅ 通过（无 B 段 + 有 CT 组 + U11）
```

`U11` 和 iv8 通过时完全一致，`q(0 0 5 -1)` 也一致 —— 这是干净通过的特征。

### 用法

```bash
# 自测
node tools/token_pool.js

# 起服务，业务侧 HTTP 取
node tools/token_pool.js --serve 8899
curl 'http://127.0.0.1:8899/token?host=book.airgreenland.com'
→ {"token":"3:...","cookie":"...","remainingSec":780,"solvedAt":...}
```

作为模块：

```js
const pool = require('./tools/token_pool');
const t = await pool.get('book.airgreenland.com');
// t.token / t.cookie / t.expiresAt
```

### 两个不能省的配置（踩过）

1. **必须有头。** `--headless=new` 在这站上 90 秒都拿不到 token。
   窗口放屏幕外（`--window-position=-2400,-2400`）不打扰。
2. **绝不覆盖 UA。** 我一开始用 `Emulation.setUserAgentOverride` 改成 Chrome/141，
   但浏览器本体是 Edge/154 → UA 说 Chrome、`sec-ch-ua` 说 Edge，**自相矛盾**，
   90 秒拿不到 token。删掉那行就过了。

> 「伪装」比「什么都不做」更容易被识破。这条在补环境里也一样成立。

### 已知限制

- **串行求解。** 同时开多个有头浏览器会互相抢焦点、抢 profile，实测更容易被识别。
  需要更高吞吐就多进程，每进程一个池。
- **依赖有头 GUI 环境。** 无桌面的服务器上跑不了（没有 X11/Wayland 时
  Chromium 起不来有头模式）。这种情况下只能回到补环境或 iv8。
- **token 与 UA 强绑定。** 池产出的 token 只能用 UA = Edge/154 去请求。
  业务侧如果用别的 UA，要改成对应浏览器的 UA 一起解。

## 三、下一步该怎么走（如果要继续攻补环境）

按可行性排序，只有三条：

### 1. 在 iv8 里 dump 编码前的明文对象（唯一"看见答案"的路）

这是目前唯一能定位字段差异的方法。具体做法：

- hook 点：sensor 内部把 38 个字段组装成对象、交给加密函数的那一刻。
- 怎么找：从 `cr` 的读取处反推。`cr` 是编码密钥，加密函数一定读它。
  在 iv8 里把 `cr` 的值改成一个哨兵值（比如 12345），然后 hook 所有
  `String.fromCharCode` / `Array.prototype.push`，找出"第一个用到 12345 的地方"。
- 拿到明文对象后，和我们在补环境里 dump 的同一批字段逐个 diff。

**这一步如果做成，就能直接知道是哪个字段的值不对，而不是继续猜。**
代价是要能定位到那个 hook 点，可能需要读一部分 JSVMP。

### 2. 换执行引擎（等价的另一条路）

CSDN 那篇《reese84 反爬对抗与绕过》走的就是这条路：Rust 自研 JS 引擎，
在底层重建环境，**内建虚拟时钟**（`performance.now` 与 `Date.now` 同步推进）。

关键不是 Rust，是**它能精确控制异步调度**：
真浏览器的 sensor 是分阶段采集、阶段之间真有等待；
我们同步 eval 一次跑完，某些分支根本没机会执行。

我们用 Node 的 vm 做不到这一点（vm 里 `setTimeout` 是我们自己实现的，
但同步 eval 的整体执行模型改不了）。

### 3. 直接放弃补环境，用浏览器池 + 载荷缓存

如果目标是"本地调用、够快、够稳"，那已经做到了。
真正该优化的是**降低求解频率**：

- 现在每次解都新开 profile，等于每次都像"新访客"。如果持久化 profile，
  服务端可能会给更长的 `renewInSec`，甚至直接复用 cookie 不再挑战。
- 实测 `renewInSec` 790~890 秒。如果能提到 30 分钟，求解频率就降一半。

这条比攻补环境划算得多。

## 四、这一轮的方法论（供以后复用）

1. **真值只能从"能通过的实现的请求体"里读。** 不能从任何中间探针推。
   我拿一个探针量出来的 7083 当靶子，调了一整天，那个数字根本不是 payload 字段。
2. **判据要选最早能拿到的那一个。** POST 响应头的 `X-Iinfo` 是 3 秒，
   业务验证 GET 是 20 秒。选对了迭代速度差一个数量级。
3. **同会话换 body 是最强对照实验。** 它把网络、会话、TLS 全固定住，
   只剩载荷一个变量。以前换请求头、换验证方式，全是在噪声里找信号。
4. **加密的载荷跨会话不可对齐。** 想在两个实现之间 diff，必须先让两边的
   编码一致（同 cr），而 cr 由随机数消耗序列决定 —— 环境一有差异就对不齐。
   所以要么 dump 明文，要么别比。
5. **"拿到 token" 永远是假阳性。** 服务端判你 bot 的时候，照样返回
   格式完全正确的 1254 字符 token。
6. **别做"看起来在推进"的实验。** 给 `Date.now` 加常数偏移不改变差值、
   给时钟做分段压缩只改形态不改校验 —— 这类实验跑一整天也没有信息量。
   先想清楚"这个改动如果生效，观察量会怎么变"，再动手。
