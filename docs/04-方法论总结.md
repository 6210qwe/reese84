# 方法论总结：这轮踩坑换来的 8 条经验

> 这份不是技术细节，而是"下次怎么做能少走一半弯路"。

## 1. 先扫本地 skill，再动手

本轮最大的浪费，是**重复踩了已经写在 `iv8-env/references/reese84-imperva.md` 里的坑**：

- `--compressed` 导致拿不到挑战页 —— 文档里有，我又踩了一次
- sensor 残包要校验完整性 —— 文档里有
- `page.load` 会重置 window，补丁要 prepend —— 文档里有

**正确顺序**：

```
1. 扫本地 skill（iv8-env / reese84-imperva-solver / ruishu-* / js-reverse-challenge）
2. 确认靶点：子域枚举 + 看 X-Iinfo / Set-Cookie 特征，别在主域瞎找
3. 摸触发条件：试 4 组请求头（裸头 / +Lang / +Enc / +Accept-html）
4. 判"能跑原始 VM 吗" —— 能就直接 iv8，别写补环境
5. 只有 iv8 不可行时才写补环境
```

## 2. "不报错"不等于"成功"

本仓库 `docs/03` 列的 12 个坑，**全部是静默失败**：
没有异常、没有日志、程序正常退出。

所以判断成功必须用**服务端可观测的证据**：

```bash
# ✓ 正确判据：带着 token 打 /api/，必须 404 且不含任何拦截特征
curl -s -o /tmp/a.html -A "$UA" -H "Accept: */*" -b "$JAR" \
     "https://book.airgreenland.com/api/"
grep -c "Pardon Our Interruption\|_Incapsula_Resource\|Incapsula incident\|main-iframe" /tmp/a.html
# 必须输出 0
```

```python
# ✗ 错误判据（我犯过）
ok = "Pardon Our Interruption" in resp.text     # 漏掉 200 响应的 iframe 形态
ok = resp.status_code == 200                     # 200 恰好是被拦的常见形态
ok = token is not None                           # 服务端会照常签发再判死
```

**拦截页有三种形态**，只判第一种会把第二种误判成通过：

1. `<title>Pardon Our Interruption</title>`（经典 403）
2. `<iframe id="main-iframe" src="/_Incapsula_Resource?...">` + `Incapsula incident ID`，**返回码 200**
3. `scriptElement.src = "..."`（挑战页）

**`X-Iinfo` 的 B10 / B12 都不能当判据**（B12 也可能是拦）。

## 3. 分清"签发"和"信任"两步

这是本轮最重要的认知修正：

```
POST /<path>?d=<host>  →  200  {"token":"3:...", "renewInSec":867}
                            ↑ 服务端照常签发，不等于你通过了
GET  /                 →  200  + iframe 拦截页
                            ↑ 真正判死在这里
```

我们的 payload 比真实浏览器还大（32816 vs 28412），token 1270~1322 字符，
**服务端签发了，但回放被拒**。

⇒ 只看"有没有 token"会得出完全错误的结论。

---

## 4. 对照实验 > 翻混淆代码

本轮三个决定性结论，全部来自对照，没有一个是读混淆码读出来的：

| 结论 | 怎么得出的 |
|---|---|
| 是载荷问题，不是请求问题 | 用 iv8 的旧 body POST → **200**；用我们的 body → **400** |
| 不是 IP / 不是改版 | 同时段 iv8 100% 通过（`/api/`→404、`/`→198987B 真实首页） |
| 知道"正确答案"长什么样 | 在 iv8 里插桩 `performance` → `total=6570`、`now` 8008 次 |

**930KB 的 JSVMP，不要试图读它。** 我试图从源码里解那个标记字符串，
读了 3 段反编译代码，最后还是靠"插桩 + 对照"解决的。

---

## 5. 插桩要插在"能通过的实现"里

在自己失败的环境里猜服务端要什么，**永远是猜**。

```
✗ 我在自己的环境里：猜 total 是什么 → 试了 7 个假设，全错
✓ 去 iv8 里插 performance → 一次拿到基准：total=6570、now 8008 次、mark/measure 0 次
```

这一步直接推翻了我最初"那两个哈希键来自 User Timing measure"的判断
（因为 iv8 里 `mark`/`measure` **一次都没调用**）。

---

## 6. 别在猜黑盒上无限投入

我排除了 7 个时间源假设（`performance.now` 返回值 / `now` 真实耗时 /
`timing.navigationStart` / `getEntriesByType('navigation')` / `mark`/`measure` /
`Date.now` / `new Date().getTime()`），`total` 的公式仍未破解。

**这时候正确做法是：停下、记录、换路线。**
iv8 已经能用，工程上先用它；把未解的问题写清楚交给后来者（`docs/02` §4）。

继续加实验的边际收益已经很低了，而且每个实验都要 60~90 秒。

---

## 7. 指纹值必须采样，不能猜

实测本机真实值 vs 我猜的值：

| 项 | 我猜的 | 真实 | 为什么猜是错的 |
|---|---|---|---|
| `hardwareConcurrency` | 8 | **16** | 与设备等级矛盾 |
| `screen` | 1536×864 | **1366×768** | 与 `innerWidth/outerWidth` 矛盾 |
| `deviceMemory` | 8 | **undefined** | Chrome 141 已不暴露，写了反而是破绽 |
| WebGL renderer | 少了型号 id | 有 `(0x00001900)` | 属自造指纹 |

`web-js-env-patcher` 硬规则 14 写得很清楚：

> **AI 猜值、随机值、默认值、mock、jsdom、node-canvas、headless-gl 不能作为最终回放值。**

这条规则直接判了 jsdom 死刑 —— 我本该在看到它的第一眼就放弃 jsdom，而不是花 15 轮修 12 类泄漏。

## 8. 一致性比"补全"更重要

不是"API 存在就安全"，而是"值之间不能互相矛盾"。

用 CDP 的 `CSS.getPlatformFontsForNode` 查到的权威答案：

| generic 族 | 本机 Edge 实际解析成 |
|---|---|
| `sans-serif` | **Noto Sans SC** |
| `serif` | **Noto Serif SC** |
| `monospace` | **NSimSun** |
| `system-ui` | **Microsoft YaHei UI** |

同一字体 `Noto Sans SC`：Chrome 10px 量得 **101.03**，Skia 量得 **96.43**。
而显式族名（`Arial` 125.95 / `Times New Roman` 137.79）两边**完全一致**。

⇒ 只有 generic 族不一致 —— 这类"声称 Windows 却没装该字体"的矛盾，是可被交叉校验的。

crawlex 的说法：

> 一致性校验会找 spoofer 引入的矛盾：UA 说 Chrome on Windows 而 WebGL vendor 说 Apple、
> `maxTouchPoints` 说有触摸而 platform 说桌面、语言列表与时区不符、
> `hardwareConcurrency` 与设备等级不符。

## 附：8 条一句话版

1. **先扫 skill**，再动手 —— 本轮最大的浪费是重复踩已记录的坑
2. **不报错 ≠ 成功** —— 用服务端可观测证据判定
3. **签发 ≠ 信任** —— 服务端会先给 token，再在回放时判死
4. **对照实验 > 读混淆码** —— 930KB JSVMP 不要试图读
5. **插桩插在能通过的实现里** —— 否则你连正确答案都不知道
6. **及时止损** —— 排除了 7 个假设还不行，就记录下来换路线
7. **指纹必须采样** —— 猜的值会和别的值自相矛盾
8. **一致性 > 补全** —— 不矛盾比"什么都有"更重要
