# 通杀框架：从"给一个网站"到"能取数"

> 本项目的最终形态不是"过掉 reese84"，而是**一套接任何风控站点的固定动作**。
> 已固化为 skill：`~/.workbuddy/skills/js-antibot-pipeline/`

---

## 1. 为什么需要框架，而不是一次性脚本

这条路上我犯的最大错误是：**每次接新站都从头摸**。

对照一下成本：

| 做法 | 接新站的成本 |
|---|---|
| 一次性脚本 | 每个站 2~3 天（重复踩 `--compressed`、残包、head 失同步……） |
| 框架化 | 第一步跑探测器（< 1 分钟）→ 按决策树走 → 只有"未知厂商"才需要人工 |

**12 条静默失败坑里有 8 条是"跨站点通用"的**（见 `docs/03`），它们本该一开始就写进框架。

---

## 2. 框架的三层结构

```
┌─────────────────────────────────────────────┐
│ L1 识别层  detect_protection.py             │  ← 给 URL，输出厂商+坐标+路线
├─────────────────────────────────────────────┤
│ L2 执行层  按厂商选：iv8 / 补环境 / AST / 浏览器│
├─────────────────────────────────────────────┤
│ L3 门禁层  服务端可观测证据 + 形状/值/时序探针  │
└─────────────────────────────────────────────┘
```

### L1：识别层（已实现，跨站验证通过）

```bash
python -X utf8 tools/detect_protection.py https://target.com/ --deep --json case/<host>.json
```

输出六段：基础响应 / 防护判定（带证据条数）/ 挑战页坐标 / **请求头模式探测** / sensor 详情 / 路线建议。

**跨站验证结果**：

| 目标 | 判定 | 证据 | 正确性 |
|---|---|---|---|
| `book.airgreenland.com` | reese84 / Imperva | 6 条（`reeseSkipExpirationCheck`、`scriptElement.src`、`x-iinfo`、`visid_incap`…） | ✅ 与本项目实测一致 |
| `www.nmpa.gov.cn` | **瑞数** | `$_ts` + 响应 412 | ✅ 412 正是瑞数典型拦截 |
| `www.qcc.com` | 未命中（未受保护） | 五种头都 200 | ✅ 首页确实不校验 |

⇒ **探测器不是只对 reese84 有效**，这是"通杀"的基础。

### L2：执行层（按厂商分流）

| 厂商 | 首选 | 备选 |
|---|---|---|
| reese84 | **iv8**（实测通过） | Node 补环境（能签发，回放 B12） |
| 瑞数 | **iv8**（瑞数5/6 都过） | `ruishu-bypass` |
| Cloudflare 5s盾 | `cf_clearance` 池 + `curl_cffi` | AST 解 jsd / 真实浏览器 |
| Akamai | iv8 | 纯算（POST 两次） |
| 未知 | §3 通用定位法 | — |

### L3：门禁层（三条，缺一不可）

1. **服务端可观测证据**：带 token 打受保护路径 → 必须 404 且无拦截特征
2. **形状探针**：`probe_tostring.js` → 不能有任何 `class X extends Y` 泄漏
3. **值探针**：`probe_fp_env.js` → 与真实浏览器基线逐项对齐

## 3. 通用定位法（任何自研签名都适用）

按效率排序，从 1 开始，**不要从 AST 开始**：

| # | 方法 | 见效 |
|---|---|---|
| 1 | 钩 base64 出口（`btoa` / `CryptoJS.enc.Base64`）`+ 打栈` | 秒级 |
| 2 | 钩网络出口（`fetch` / `XHR.send` / `sendBeacon`） | 秒级 |
| 3 | 钩 `document.cookie` 的 setter | 秒级 |
| 4 | 钩 `JSON.stringify` | 秒级 |
| 5 | AST 定位（PZz0203 的 `finders.js` 思路） | 分钟级，只在无法插桩时用 |

**必须输出四层坐标**：`source → entry → builder → writer`。
只报"疑似加密函数"不算找到。

## 4. 补环境路线的定位（重要认知）

> **浏览器能实现的，本地一定能实现。** 差别只在两个维度：
> **① 环境访问的开销**（纯 JS vs Blink binding 层，差一个数量级）
> **② 对象形状**（descriptor / 原型链 / toString / 自有属性集）

本项目把 ① 做到了可控（`--clock-jump` 可精确把 `total` 调到 7118），
但 ② 暴露了一个**从第一版就带着的洞**：80+ 个 `class X extends Y` 的源码全部通过
`Function.prototype.toString` 泄漏。修完之后页面执行从 54s 降到 2.6s，但仍未通过回放。

⇒ **补环境能解决"值"和"形状"，很难解决"时序比例"。**
这也解释了为什么商业方案（Hyper Solutions）和 CSDN 那篇都选择**自研引擎或托管的指纹库**，
而不是在 Node 里补。

**所以框架的判断是**：
```
能跑 iv8 → 用 iv8（永远优先）
必须纯 Node → 补环境 + 接受"可能过不了最严的站"
必须纯算 → 先确认编码不是每次重载都变（reese84 是变的，直接放弃）
```

## 5. 每次接新站的固定动作（复制即用）

```bash
# ① 识别（< 1 分钟）
python -X utf8 tools/detect_protection.py https://target.com/ --deep --json case/host.json

# ② 按决策树走
#    reese84 → iv8/solve_iv8.py
#    瑞数    → iv8
#    未知    → 通用定位法（钩 btoa / fetch）

# ③ 若走补环境
node tools/sample_fp.js        # 采真实基线
node tools/probe_tostring.js   # 形状 / 原生性
node tools/probe_fp_env.js     # 值与真机差异
node src/runner.js -v          # 跑通

# ④ 门禁验证（缺一条都不能说成功）
```
