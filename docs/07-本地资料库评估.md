## 2. 有价值的五块（按对 reese84 的用处排序）

### ⭐⭐⭐ 2.1 `排坑skill/references/failure-matrix.md` —— 故障矩阵

这是整个资料库里**最可直接复用**的东西。它的形式是：

| 症状 | 优先判断 | 下一步 |
|---|---|---|
| 浏览器 `[5009]` | URL 已频繁 | 立即停用并轮换网址池，不继续归因本地 |
| `wasmReady=false` | 走 JS fallback | 查 Wasm URL、响应、MIME、instantiate 顺序 |
| packet head 非 TC07 | 分支或环境探针错误 | 对比 Wasm import、明文任务、资源版本；**禁止提交** |
| 静态字符串不一致 | 浏览器读取未补齐 | **定位最早读取点**，修 descriptor/native/DOM/Canvas/WebGL/字体 |
| 明文一致但密文替换失败 | Wasm 运行边界或随机态错位 | 在同一调用点替换完整 pre-Wasm 明文，再逐层缩小 |

还有一条**回退原则**，写得比我之前的方法好：

> 当复现中断或证据冲突时，返回最早不确定阶段：
> `URL/页面 → i18n/get → 图片/距离 → 轨迹 → pre-Wasm 明文 → Wasm instantiate → TC07 自校验 → verify → 服务端结果`
> **一次只改一个变量，并保存修改前后的同轮证据。**

⇒ **已吸收进新 skill 的故障矩阵**（把判据换成本项目的：payload 长度 / performance / B12 / timer 计数）。

### ⭐⭐⭐ 2.2 `jsvmp-algo-restore-skill` —— JSVMP 还原方法论

核心原则写得对：

> 1. **还原算法，不是模拟虚拟机** —— 不在 Python 中重建 VMP 解释器，而是理解算法数学本质后简化实现
> 2. **日志驱动** —— 插装日志是理解 VMP 行为的主要手段
> 3. **分层推进** —— 先跑通得到结果 → 再分析数据流 → 再提取纯算法
> 4. **交叉验证** —— 每一步都与原始输出对比

并且明确区分了职责：
> 与补环境 skill 互补：补环境让代码跑起来，本 skill 理解并还原算法本身。

⇒ **正是本项目需要的分工**：我们走补环境（让代码跑起来），不碰 JSVMP 还原。

**但要注意**：对 reese84 而言，`docs/06` 已证明 **PZz0203 的结论是"编码函数每次重载都变"**，
所以"还原算法"对 reese84 的经济性不成立。这条资料对**其他**目标（瑞数/5s盾/腾讯）更有用。

### ⭐⭐ 2.3 `7.1-3 5s盾反混淆ast插件` —— 2604 行 AST 插件

这是一份**成熟的 obfuscator.io 反混淆实现**，含：

- string-array 轮转还原
- RC4 accessor 解码
- 控制流平坦化还原
- `reqable` 动态替换脚本（**直接在抓包工具里替换 JS**）

**对 reese84 的用处**：reese84 的字符串表用的就是 **obfuscator.io 的 string-array + RC4**。
这份插件能解出字符串表（`docs/01` 里那个"命中校验和 0xb9a6b、轮转 421 次"就是同一套）。

**注意**：解出字符串表 ≠ 解开 payload。payload 是 xorshift128 字节重排，不在这套工具的能力范围内。

### ⭐⭐ 2.4 `1.3-3_ast基础课程资料` + 各 `ast_plugin.js`

Babel AST 入门的完整材料。**这套是做"自动定位加密函数"的前置能力**（对应 PZz0203 的 `finders.js`）。

我们已经有了"钩 `btoa` 打栈定位出口"这个更快的办法，
但 **AST 定位法在"没法插桩"的场景（比如要静态分析）才不可替代**。
