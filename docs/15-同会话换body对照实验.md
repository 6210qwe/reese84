# 决定性对照：把"猜"换成"同会话换 body"

这一轮做了四件事，其中两件推翻了我之前的结论。全部是可复现的实测。

---

## 一、拿到了一条能通过的路线（但不是补环境）

`tools/browser_solve.js`，有头 Edge + CDP，**8.8 秒拿到 token，长度 1366**，
再用 curl 回放 `/` → **302 len=213，无拦截标记**。

两个关键点，都是踩坑踩出来的：

1. **必须用有头模式。** `--headless=new` 在这站上 90 秒都拿不到 token。
   有头窗口放到屏幕外（`--window-position=-2400,-2400`）不打扰。
2. **绝对不能覆盖 UA。** 我第一次用 `Emulation.setUserAgentOverride` 把 UA 改成
   Chrome/141，但浏览器本体是 Edge/154 → UA 说 Chrome、`sec-ch-ua` 说 Edge，
   自相矛盾，90 秒拿不到 token。改掉这行就过了。

第二条的教训比第一条大：**「伪装」比「什么都不做」更容易被识破**。

---

## 二、★ 推翻结论一：`performance` 的真实值不是 46/7083

之前我一直拿「真机 46 / 7083」当靶子（那是早期探针量 `performance.now` 跨度得来的，
不是 payload 里的字段）。这次直接从浏览器抓下来的 POST body 里读：

```
浏览器 performance = {"1030820235": 4970, "4203433130": 0, "total": 4977}
iv8     performance = {"1030820235": 46,   "4203433130": 1, "total": 6570}
我们    performance = {"1030820235": 597,  "4203433130": 1, "total": 630}
```

注意：**浏览器的 `phase1 ≈ total`（4970 / 4977），比例 99.9%，和我们一样（597/630，95%）。**

而 iv8 是 46 / 6570，比例 0.7% —— 完全相反的形态，**iv8 却通过**。

⇒ 结论：**时序形态根本不被校验。** 这一条把"performance band"整条假设否掉了，
也否掉了我为它调的 `--clock-jump` / `--date-scale` / `--warp-ms` / `--fake-start` 全部。

（工具留着没用，但方向是错的。这就是为什么要去"能通过的实现"里拿真实值，
而不是拿一个自己臆想的数字当靶子。）

---

## 三、★ 推翻结论二：载荷不绑会话，可以跨会话回放

做一个对照：**用浏览器的 body，POST 到我们自己用 curl 新建的挑战会话**。

```bash
curl -c _cj.txt https://book.airgreenland.com/api/    # 新会话
curl -b _cj.txt -X POST --data-binary @_browser_body.json \
  "https://book.airgreenland.com${SENSOR_PATH}?d=book.airgreenland.com"
```

结果：

```
HTTP=200  {"token":"3:..."}
X-Iinfo: 54-...-... PNNN RT(... 231) q(0 0 0 -1) r(2 2) U6      ← 无 B 段
```

同一个会话风格、同一个 curl、只换 body，**结果从 B12 变成无 B**。

⇒ 载荷不绑 TLS、不绑会话 cookie、不绑连接。**唯一的变量就是载荷内容本身。**

---

## 四、★★ 找到每次请求就能拿到的即时判据

这是本轮最实用的产出。**POST 的响应头就带答案**，不用再等业务验证 GET：

| 只换 body | POST 响应 `X-Iinfo` |
|---|---|
| 浏览器载荷 | `PNNN ... q(0 0 0 -1) r(2 2) U6` ← **无 B** |
| 我们的载荷 | `NNNN ... q(0 -1 -1 -1) r(0 -1) **B12(14,0,0)** U18` |

以前是「跑完整流程 → 再 GET 业务页 → 看有没有被拦」，
现在**一次 POST 就能判**，迭代速度提高一个数量级。

而且要注意一个反直觉的点：**服务端在被判 B12 的同时仍然返回了合法 token**
（1355 字符，格式正确）。所以"拿到 token"从来不等于"通过"——
这也是我之前四个错误判据里最坑的一个。

## 五、现在唯一已知的差异：载荷体积差 5556 字节

```
浏览器  p = 38176
我们    p = 32620
差      =  5556 字节（我们少 14.5%）
```

而且这个差值很稳定（浏览器两次采样分别是 36901 / 38393 body，量级一致）。

配合 iv8 的数据看：iv8 的 p 是 27912 —— **比我们还小，但 iv8 通过**。

⇒ 体积本身不是判据。**是我们"少了某一整块采集"，而 iv8 虽然小，但它的块是全的。**

那少的 5556 字节可能是什么？几个候选，按可能性排：

1. **字体探测被截断。** iv8 的 `measureText` 调用 732 次，我们 338 次。
   字体探测的算法是：拿一串测试字符串，在候选字体和 generic fallback 下各量一次宽度，
   宽度不同就认为装了该字体。我们调用数只有一半，说明候选集或循环轮数少了一半，
   最后报给服务端的「已安装字体清单」也短一半。
2. **canvas 取图的实际内容。** 浏览器 12~16 次 `toDataURL`，我们 12 次，
   但我们的 Skia PNG 尺寸和 Chrome 的 PNG 尺寸可能差很多（压缩率不同）。
3. **`document_children` / `window_object_get_own_property_names_*`。**
   我们是 1253 项（真机 1239），这块我们反而更大，应该不是缺口来源。

下一步应该做的就是：**逐块把采集结果置空，看体积掉多少**，
掉得最多的那块就是候选，然后单独修那一块。

## 六、这一轮的方法论收获

1. **「去能通过的实现里拿真实值」这条原则，我执行得不够彻底。**
   我拿 iv8 插桩拿过一次基准，但那次量的是 `performance.now` 的跨度，
   不是 payload 里的字段，于是我拿着一个错数字调了整整一天。
   正确的做法是：**直接把合法请求的 body 抓下来读**，那是唯一没有中间层的真值。
2. **判据要选"最早能拿到的那个"。** 业务验证 GET 是最后一步，
   POST 响应头是中间那一步，选它就能把单次实验成本从 20 秒降到 3 秒。
3. **"拿到 token" 永远是假阳性信号。** 服务端会给被判 bot 的请求也签发 token。
   要看 `X-Iinfo` 的 B 段。
4. **同会话换 body 是补环境里最强的对照实验。** 它把「网络/会话/TLS」全部固定住，
   只剩「载荷」一个变量。以前我一直在换请求头、换验证方式，那些都是在噪声里找信号。
