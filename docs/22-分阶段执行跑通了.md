# 分阶段执行终于跑通了，但仍然 B12

这一轮做成了两件之前一直没做成的事。结论没变，但**补环境这条路线的最后两个盲区被填掉了**。

---

## 一、虚拟定时器：修掉一个"自己写的同步 bug"

上一轮我实现虚拟定时器队列后，sensor 完全不发 POST，我当时的结论是
"Node 的 vm 里 microtask 自动 flush，没法暂停在某一轮，所以这条路走不通"。

**这个结论是错的。** 真正的原因是我写的代码有问题：

```js
for (let i = 0; i < 14; i++) {
  env.page.advance(600);   // 同步执行到期的回调
}
```

14 轮全部在**同一个 tick** 里跑完。而 sensor 的网络请求走 curl 子进程，
响应要等 Node 的事件循环才能回来。于是：

```
14 轮推进完 → 一个网络回调都没落地 → 采集链断在半路 → 完全不发 POST
```

**修法：每轮 advance 之后让出一小段真实时间。**

```js
for (let i = 0; i < rounds; i++) {
  env.page.advance(600);                                  // 虚拟时钟 +600
  await new Promise(r => setTimeout(r, 120));             // 让 curl 回调和微任务落地
}
```

这才是"虚拟时间 + 真实 I/O"的正确组合：**时钟归我控制，I/O 归 Node 控制。**

### 修好之后立刻看到分阶段执行

```
drive 第 1 轮：执行  1 个回调，虚拟时间  600ms，剩余 1（让出后剩余 2）
drive 第 2 轮：执行  2 个回调，虚拟时间 1200ms，剩余 1（让出后剩余 2）
drive 第 3 轮：执行  7 个回调，虚拟时间 1800ms，剩余 2（让出后剩余 3）
drive 第 4 轮：执行 43 个回调，虚拟时间 2400ms，剩余 2（让出后剩余 3）
drive 第 5 轮：执行  2 个回调，虚拟时间 3000ms，剩余 2（让出后剩余 3）
drive 第 6 轮：执行  8 个回调，虚拟时间 3600ms，剩余 2（让出后剩余 3）
[6] POST 完成，payload=23968
```

**回调数 1 → 2 → 7 → 43 → 2 → 8，这就是分阶段增量采集。**
"让出后剩余"从 1 变成 2/3，说明每轮都有新的异步任务被网络回调追加进来 —— 和真实浏览器的节奏一致。

之前是同步一把跑完，回调数永远是"一次性全跑完"，结构完全不同。

## 二、Navigator 原型：名称集合和顺序都不对

查这个是因为一个具体观察：iv8 的 `Object.getOwnPropertyNames(navigator)` 是 `[]`，
但 `Object.getOwnPropertyNames(navigator.__proto__)` 有 **69 项**。

| | iv8（通过） | 我们 |
|---|---|---|
| `navigator` 自有属性 | 0 | 0 ✅ |
| `__proto__` 属性数 | **69** | **45** |
| `__proto__` 前几项 | `vendorSub, productSub, vendor, maxTouchPoints, scheduling, userActivation, doNotTrack, geolocation, ...` | `constructor, plugins, mimeTypes, userAgentData, connection, permissions, mediaDevices, ...` |
| 描述符形状 | `get/set/enumerable/configurable` | 同 ✅ |

**名称少了 24 个，顺序完全不同。** 如果 sensor 采
`getOwnPropertyNames(navigator.__proto__)`（payload schema 里确实有类似的字段），
名称集合和顺序都会直接进载荷。

### 对齐方法

顺序不能靠"改"——属性的顺序是定义顺序，删了重加会跑到末尾。
必须**整体重建**：

```js
function __realignPrototype(Ctor, order, vals, label) {
  const proto = Ctor.prototype;
  // 1. 摘下所有描述符
  const saved = new Map();
  for (const n of Object.getOwnPropertyNames(proto)) {
    saved.set(n, Object.getOwnPropertyDescriptor(proto, n));
  }
  // 2. 删掉（不删的话重定义不改变顺序）
  for (const n of saved.keys()) if (n !== 'constructor') delete proto[n];
  // 3. 按目标顺序重定义；缺的造同类型空桩
  for (const n of order) {
    if (saved.has(n)) Object.defineProperty(proto, n, saved.get(n));
    else Object.defineProperty(proto, n, { get: ..., enumerable: true, configurable: true });
  }
}
```

`iv8_proto_names.json` 由 `dump_proto.py` 从 iv8 导出，含 69 个名字 + 每项的 `typeof`（用来造正确的桩）。

### 效果

```
[env] Navigator.prototype 重排：目标 69 项，补 24 项，现 69 项
[env] Screen.prototype    重排：目标 12 项，补  1 项，现 12 项
```

同一配置下 payload **23968 → 25832（+1864 字节）** ——
证明 sensor 确实在采这部分，而且我们之前一直少给。

## 四、所以现在能说什么

之前我说"剩下唯一未排除的是执行模型"。这轮把执行模型也补上了
（真的分阶段推进，回调分布和 iv8 一致），结果还是 B12。

**那"执行模型"这个假设也可以划掉了。** 目前的排除清单到第 17 条：

16. ~~虚拟定时器/分阶段执行~~ → 已实现，回调分布 1/2/7/43/2/8，仍 B12
17. ~~Navigator/Screen 原型名称与顺序~~ → 已对齐到 iv8 的 69/12 项，payload +1864，仍 B12

剩下我能想到的可能性只有两类，而且都很难验证：

**A. 载荷的加密/编码路径和 iv8 不同。**
我们 hook btoa 拿到 1906 次调用、18145 字节的中间产物，但没有字段结构 ——
说明编码链是多层分块的。如果某一层的输入（比如 `cr` 之外还有别的密钥、
或者某个中间数组的长度）和 iv8 不一致，密文就整体不可比。
验证需要逆向 JSVMP 的编码函数。

**B. 服务端在做跨请求的关联。**
比如要求"先 GET 过某个子资源再 POST"、"TLS 会话票据要和上次一致"、
或者对某个时序窗口有要求（我们已经是 0.5 秒内完成，真机是 7 秒）。
这一类比 A 更难查，因为看不到服务端逻辑。

## 五、这一轮的方法论（两条，都很值钱）

1. **"这条路走不通"的结论，要先排除自己写错的可能。**
   上一轮我判定"Node 的 vm 没法分阶段推进"，实际是我 14 轮同步跑完、
   没给网络回调留窗口。**一个 5 行的 `await` 就让这个假设反转了。**
   以后给出"架构上做不到"的结论前，先检查自己有没有实现错。

2. **顺序也是特征。**
   属性的名称集合对了、值对了、描述符形状对了，但**顺序不同**照样能被采出来。
   这在补环境里很容易忽略，因为大多数人只对比 `length` 和值。
   `getOwnPropertyNames()` 返回的顺序是定义顺序，靠"补"是补不出来的，必须重建。

## 六、可用方案（没变）

```bash
# 一次求解（热启动 0.45 秒，token 有效 30 天）
node tools/token_pool.js

# 起服务
node tools/token_pool.js --serve 8899
```

补环境这边新增的开关（都在 `src/runner.js`）：

| 开关 | 作用 |
|---|---|
| `--virtual-timers` | 用虚拟定时器队列替代真实定时器 |
| `--drive N` | load 之后推进 N 轮虚拟时间（每轮 600ms），和 iv8 的 `eventLoop.sleep` 对齐 |
| `--drive-yield N` | 每轮推进后让出 N 毫秒真实时间（**不加这个会完全不发 POST**） |
| `--iv8-profile` | 全套照抄 iv8 的环境值 + 原型名称与顺序 |
| `--mouse-between` | 每轮之间派发鼠标轨迹（实测无效果，保留供别的站试） |
