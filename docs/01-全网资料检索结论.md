按可信度排序，重点标注**"对本例成立还是不成立"**——很多结论在其他站点对、

## 1. crawlex —— 最完整，直接命中我们的卡点

- [Imperva's reese84 sensor: what the obfuscated payload collects](https://blog.crawlex.net/blog/imperva-reese84-sensor)

### 1.1 原文关键段（计时检测）

> The fourth category is the quiet one: **consistency and timing**.
> The script does not only collect values, it cross-checks them, and **it measures how long the collection took**.
> A performance-derived timing object rides along in the payload.
> **Real browsers on real hardware produce collection timings within a band**;
> an environment where the JavaScript engine is instrumented, or where probes are being intercepted
> and answered by hooks, produces timings **outside it**.
> A hook that intercepts a property read and returns a forged value adds a few microseconds to that read,
> and across a collection that touches hundreds of properties, the accumulated overhead is measurable.
> **The timing object is cheap to collect and expensive to forge convincingly, because forging it well
> requires knowing the band the server expects, which the server does not advertise.**

**对本例的判定：✅ 成立，而且我们是"反向超标"。**

crawlex 描述的是"hook 让 timing **变慢**"，我们的问题是"纯 JS 让 timing **变快**"：

| 方案 | `performance.total` | 与真机（7083）比 |
|---|---|---|
| 真实浏览器 | 7083 | — |
| iv8（C++ 绑定层） | 7442 | +5% |
| 本方案（纯 JS 对象属性） | 484~710 | **-93%** |

两者都在 band 外，只是方向相反。**这说明"补更多 API"解决不了这个问题，
因为问题不在 API 存不存在，而在访问速度。** 详见 `docs/03-性能计时之谜.md`。

### 1.2 原文其他要点 + 本例验证

| 说法 | 本例 |
|---|---|
| 一条路径两个动词，GET 取 collector / POST 提交 | ✅ `?s=` 在 GET、`?d=` 在 POST |
| body 用 `text/plain` 规避 CORS 预检 | ✅ `Content-Type: text/plain; charset=utf-8` |
| 字段 `p / st / sr / cr / og / old_token / version` | ✅ 完全一致 |
| payload 用 **xorshift128 字节重排**，不是 RC4 | ✅ 与"zlib/gzip/bz2/lzma 全解不开、熵 7.82"吻合 |
| 编码绑 build，换版本旧编码器作废 | ✅ 路径与 `?s=` 都会轮换 |
| 跨字段一致性校验（UA 说 Windows 但 WebGL 说 Apple 等） | ✅ 我们踩过：hardwareConcurrency 猜 8（本机 16）、deviceMemory 写了但 Chrome 141 已不暴露 |
| `localStorage` 缓存 token，sensor 只跑一次 | ✅ 重跑前必须清 localStorage |
| 边界：JA3/JA4、HTTP/2 frame、header 顺序在边缘读取 | ⚠ **对本站不成立**：iv8 全程用 curl（与 Chrome TLS 不同）依然 100% 通过 |

## 2. CSDN《reese84风控绕过》—— 指出了"虚拟时钟"这个方向

- [reese84风控绕过](https://blog.csdn.net/qq_27739983/article/details/162672215)

### 2.1 原文关键段

> 我们的思路不是「伪装」，而是「重建」——用 Rust 自研一套 JS 引擎，并在其上从底层重建一个自洽的真实浏览器环境…
>
> **时钟一致性 —— 内建虚拟时钟，把脚本铺开的数秒交互压缩到亚秒跑完，而脚本读到的时间仍是
> 「真实经过了那么久」，`performance.now` 与 `Date.now` 同步推进、不露时序破绽。**

### 2.2 对我们的意义

这条直接指出了"total 应该落在 6~8 秒量级"这个目标，也给出了方法论：
**不是伪造一个数字，而是让脚本读到的时间与真实浏览器一致。**

**但我们的实验证明"简单缩放 `performance.now()` 返回值无效"**：

```
缩放 now() 13x / 14x  →  total 575 / 558（无变化）
加真实自旋 200/600/1500μs →  total 510 / 544 / 492（无变化，且调用次数从 78 掉到 12）
```

⇒ sensor 算 `total` 用的**不是** `performance.now()`。
必须先定位它真正读的时间源，虚拟时钟才谈得上实现。这一步我们没走完，见 `docs/03`。

### 2.3 另一条有用信息

该文提到"JS 补环境（在 Node 里补齐 window/document/navigator 再跑脚本）同样能求解，
两条路都走得通。差别主要在速度与工程量"。

—— 这说明纯补环境路线**原理上是通的**，我们的失败是"计时一致性"这一关没过，不是路线错。

## 3. CSDN《reese84 深度逆向分析｜JSVMP 虚拟机混淆》

- [原文](https://blog.csdn.net/shanwei_spider/article/details/164043764)

### 3.1 高频踩坑点（逐条对照本例）

| 原文说法 | 本例验证 |
|---|---|
| **断点调试拿到的 reese84 基本不可用**，脚本检测到断点会内部篡改状态、输出假 Cookie。要用 console 插桩 | ✅ 采纳：全程用外部 hook + 日志，不打断点 |
| 只复制 Cookie 字符串复用会失效（有时间校验 + 会话随机因子） | ✅ `renewInSec` 790~890s，实测浮动 |
| **补环境只补显性 navigator 属性，忽略隐性 API**（performance / hardwareConcurrency / visibility）→ 服务端指纹不匹配返回 403 | ✅ 正是我们的问题：`performance` 是隐性项里最难的一个 |
| 混淆 JS 直接扣到 Node 跑，行为与浏览器不一致 | ✅ 印证：补齐对象也不等于行为一致（速度差 12 倍） |
| 纯算维护成本极高，脚本一更新全部作废 | ✅ 结论采纳：不碰 payload 解密 |

**这篇的核心判断值得记住**：
> reese84 早已不是简单的签名算法，它是一套部署在前端的轻量级风控系统。
> 核心难点不在于某一个哈希加密，而在于 **JSVMP 虚拟机 + 反调试 + 浏览器环境指纹**三者深度耦合。

## 4. tsight《解构 Performance API：高仿真环境重构与时钟偏移对抗》

- [原文](https://tsight.io/articles/20154620)

### 4.1 原文关键段

> **精度陷阱与分辨率检测**：现代浏览器为防御 Spectre 等侧信道攻击，会对 `performance.now()` 精度人为降低
> （通常在 1ms 到 100ms 间舍入）。**如果你的补环境直接调用 Node.js 的 `process.hrtime()` 且未做舍入处理，
> 其返回的极高精度反而成了最明显的指纹**，直接暴露这是非浏览器环境。
>
> **数据一致性校验**：检测脚本会交叉验证 `performance.timing`（Legacy）与
> `performance.getEntriesByType('navigation')`（L2）。若 `navigationStart` 在两处不一致，
> 或 `domInteractive` 早于 `responseStart`，立即判定环境伪造。

### 4.2 本例验证

| 说法 | 本例 |
|---|---|
| `performance.now()` 必须舍入 | ✅ **已修**：量化到 0.1ms。修前 500 次调用 500 个唯一值，修后接近 Chrome 的 4 个 |
| `timing` 与 `getEntriesByType('navigation')` 必须一致 | ✅ **已修**：`__navigationEntry()` 由同一个 `timing` 对象派生，保证字段自洽且单调递增 |
| `navigationStart` 一致性 | ⚠ 实测：sensor **只读**了 `timing.navigationStart` 一个字段；把它提前 60 秒，`performance.total` 不变（549→546）⇒ 它拿这个值做校验/校时，不是用来算 total |

## 5. Capsolver 文档 —— 商业方案怎么做的

- [Incapsula/Imperva 文档](https://docs.capsolver.com/en/guide/captcha/imperva)

它的流程值得参考（说明"标准解法"就是跑原始 JS，不碰加密）：

```
1. GET 挑战页 → 用正则 scriptElement\.src = "(.*)" 拿 sensor URL
2. GET sensor script
3. POST /createTask（AntiImpervaTaskProxyLess，带 reeseScriptUrl + script）
4. 轮询 /getTaskResult → 拿 reese84Payload + userAgent
5. 用同一 UA POST payload 到同一路径 → 拿 cookie
6. 带 cookie 访问目标
```

**注意：它把 `userAgent` 和 payload 一起返回**，且要求回放时用**同一个 UA**。
说明 UA 与 payload 在服务端是**绑定校验**的。

⇒ 对我们的启示：补环境的 `navigator.userAgent` 必须与 HTTP 头 `User-Agent` 完全一致，
且 `baseline.json` 里的 UA 一旦改动，所有衍生值（`appVersion`、`userAgentData.brands`、WebGL 字符串）都要一起改。

- [仓库](http://git-hub.com/ZairKSM/IncapsulaReverse)

针对**已过时的 Incapsula 版本**，但有几个方法论仍然有用：

- 在 Jest + 自定义 mock 里跑脚本，精确观察 payload 生成

## 7. 综合结论：问题到底在哪

把全网资料和我们的实测对齐后，结论收敛到一点：

> **我们的失败不在"缺环境 API"，而在"环境访问速度"这一个物理维度上。**

证据链：

1. payload 结构、字段、请求形态、TLS、cookie 全部正确（服务端 200 签发 token）
2. 唯一差异是 `performance` 的三个数字（484~710 vs 7083~7442）
3. crawlex 明确说这是 band 检测，且"便宜采集、昂贵伪造"
4. 我们排除了 7 个时间源假设（详见 `docs/03`），说明传感器用的时间源还没找到
5. 而 12 倍的差距本身，来自"纯 JS 对象属性 vs Blink binding 层"的物理差异

**所以下一步的唯一有意义的方向**：定位 `total` 真正的时间源（方法见 `docs/03` §4），
然后在该源上做**统一时钟偏移/缩放**，而不是逐个 API 加成本。
